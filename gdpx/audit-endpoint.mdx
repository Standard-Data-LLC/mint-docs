`POST /v1/evaluate` reviews one task specification or benchmark methodology paper and returns structured blockers, warnings, evidence, and suggested fixes. Use it while you are still revising task content.

<Info>
  Document feedback does not create or modify source bundles, task revisions, runs, or certificates. The authoritative GDPx publication gate is the exact review bundle submitted through `/api/v3/gdpx-submissions`.
</Info>

<Warning>
  The legacy `aggregate_verdict.ready_to_submit` field describes only the document that `/v1/evaluate` received. It never authorizes a ZIP, even when its value is `true`.
</Warning>

The feedback service may retain evaluation output and operational records for retrieval, rate limiting, and support. The submitted document does not become a canonical task.

For the complete package, use the [task taxonomy](/gdpx/quickstart). For content and grading requirements, use [Benchmark best practices](/gdpx/benchmark-task-rubric-best-practices).

## Configure one API origin and key

Both API namespaces use the same partner-facing origin and tenant-scoped key:

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"
```

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/v1/whoami` | Read identity, scopes, rate limit, and canonical-submission state |
| `POST` | `/v1/evaluate` | Review one task specification or benchmark paper |
| `POST` | `/v1/benchmark-rollout-analyses` | Classify one observable rollout and assess failure legitimacy |
| `GET` | `/v1/evaluations/{evaluation_id}` | Retrieve an evaluation |
| `GET` | `/v1/healthz` | Check service health without authentication |
| `GET` | `/api/v2/intake-capabilities` | Read server-authoritative workspace-intake readiness |
| `GET` | `/api/v3/gdpx/capabilities` | Read the GDPx task-and-evidence publication contract |
| `GET` | `/api/v3/gdpx/schemas/review-bundle` | Fetch the canonical review-bundle JSON Schema |
| `POST` | `/api/v3/gdpx-submissions` | Upload complete task and rollout evidence for GDPx publication |
| `GET` | `/api/v3/gdpx-submissions/{gdpx_submission_id}` | Read one immutable submission workflow |
| `GET` | `/api/v3/tasks/{task_revision_id}/review-readiness` | Read current-policy readiness and blockers for one exact revision |
| `GET` | `/api/v3/tasks/{task_revision_id}/runs/{run_id}/rollouts/{rollout_id}` | Read the complete sanitized Master and criterion evidence |
| `GET` | `/api/v3/gdpx/catalog/current` | Read the immutable benchmark revision selected by the active catalog head |

Validate the key and discover the next step before presenting a submission action:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/v1/whoami"
```

`canonical_submission.state` is `ready`, `missing_access`, `temporarily_unavailable`, or `incompatible`. Follow its same-origin links; do not construct an `/api/v2` URL from an old task-feedback hostname.

Treat `temporarily_unavailable` as a hard stop. It can mean GDPx admission, the pinned processor release, queue dispatch, object scanner, or tenant allowlist is not ready. Retry only after the advertised capability changes; a client must not route around that state through the legacy v2 importer.

The v3 capability response and `GET /api/v3/gdpx/schemas/review-bundle` are authoritative for the active publication contract. The current regime is `gdpx-review-bundle/1.1.0`: exactly one task, one run, and one rollout per ZIP, with exact task-content and full workspace-inventory bindings. Do not infer accepted fields or adapter availability from this page, a cached schema, or a v2 response.

The v2 workspace path creates draft Audit revisions only. It cannot approve an execution, reach `review_ready`, change the GDPx catalog, or route around a disabled v3 admission gate.

Internal-QA exact-byte fixture retention also uses v3, with a source-bound attestation and active operator grant. It permits authenticated tenant review while that grant is valid but never authorizes external-catalog publication. `/v1/evaluate` and `/v1/benchmark-rollout-analyses` carry no such authority and must not be used to transport those credential-like fixture bytes.

Use [Analyze a benchmark rollout](/gdpx/benchmark-rollout-analysis) after a rollout completes. That endpoint accepts one strict JSON rollout projection and returns judge-assisted QC evidence. It does not retain or publish the rollout and does not replace the [evaluation bundle workflow](/gdpx/evaluation-bundle-upload).

A complete v3 publication proceeds from an archive-only submission to a managed QC1 run and retained receipt. Audit then verifies the committed evidence generations and creates an immutable operator-authenticated managed-execution approval. Replay or resubmit the exact bundle when the capability response instructs you to do so; only then can it reach current-policy readiness, immutable benchmark membership, and the active catalog head. Partner-supplied validation claims remain archive-only until the managed approval exists. A compatibility-reader projection stays hidden until that catalog head admits the same task, rollout, Master hash, and evidence hash.

## Submit a document

Use multipart form data. The file field must be named `file`.

<CodeGroup>

```bash cURL
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/v1/evaluate" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --form "file=@/absolute/path/to/task-spec.pdf;type=application/pdf" \
  --form 'options={"checks_to_run":["all"],"verbosity":"full","include_suggested_fixes":true}' \
  --max-time 1500 \
  --output evaluation.json
```

```bash HTTPie
http --form POST "${STANDARD_DATA_API_BASE}/v1/evaluate" \
  Authorization:"Bearer ${STANDARD_DATA_API_KEY}" \
  file@/absolute/path/to/task-spec.pdf \
  'options={"checks_to_run":["all"],"verbosity":"full","include_suggested_fixes":true}'
```

</CodeGroup>

`options` is optional JSON. Use `verbosity: "full"` while fixing a submission.

To review a taxonomy-aligned task, include the delivery-package outline, required task metadata, rollout evidence bindings, failed-rollout analyses, and dataset-level failure taxonomy and distributions in the Markdown or JSON document. These are document contents, not separate v1 request fields.

<Warning>
  The v1 parser does not enforce the complete GDPx review-bundle contract. Review `ungraded_sections` and `guidelines_version_applied`; an absence of v1 findings is not package acceptance.
</Warning>

## JSON request

Use JSON when the input is already text or base64-encoded bytes.

```json
{
  "task_input": {
    "format": "markdown",
    "content": "# Task title\n\nTask instructions...",
    "filename": "task.md"
  },
  "options": {
    "checks_to_run": ["all"],
    "guidelines_version": "v14",
    "verbosity": "full",
    "include_suggested_fixes": true
  }
}
```

`task_input.format` accepts `pdf`, `docx`, `markdown`, or `json`. PDF and DOCX content must be base64-encoded in JSON transport. The route accepts one document, not a Harbor directory or ZIP.

## Response

```json
{
  "kind": "task_spec",
  "evaluation_id": "eval_...",
  "aggregate_verdict": {
    "ready_to_submit": true,
    "blocking_issues_count": 0,
    "warning_count": 3,
    "info_count": 1,
    "estimated_fix_time_minutes": 20
  },
  "ungraded_sections": [],
  "guidelines_version_applied": "v14",
  "canonical_submission": {
    "state": "ready",
    "reason_code": "READY",
    "tenant_id": "tenant_...",
    "effective_scopes": [
      "evaluations:read",
      "evaluations:write",
      "imports:write",
      "tasks:read",
      "uploads:write"
    ],
    "required_scopes": ["imports:write", "tasks:read", "uploads:write"],
    "missing_scopes": [],
    "api_base_url": "https://api.standarddata.io",
    "document_feedback_authorizes_submission": false
  }
}
```

`kind` is `task_spec` or `benchmark_paper`. Both response kinds include the caller-specific `canonical_submission` projection. Retrieve the result later with:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/v1/evaluations/eval_..." \
  --output evaluation.json
```

## Limits and errors

- Maximum document size: `10 MB`
- Request ceiling: approximately `15 minutes`
- Rate limit: returned by `/v1/whoami`
- v1 evaluations do not support idempotency keys; do not retry while the original request remains open

Legacy v1 failures retain their backward-compatible `detail` field. If a client sends `/api/v2` to a legacy task-feedback origin, the service returns `421 WRONG_API_ORIGIN` with the canonical origin and remediation; it never redirects a bearer credential.
