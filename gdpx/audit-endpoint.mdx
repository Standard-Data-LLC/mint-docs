`POST /v1/evaluate` reviews one task specification or benchmark methodology document. It returns structured feedback about missing evidence, internal contradictions, and suggested fixes.

<Warning>
  This endpoint evaluates the document you send. It does not inspect a workspace ZIP, create a task revision, retain rollout evidence, pass a QC stage, or add a task to the active evidence catalog.
</Warning>

## Choose the right endpoint

| Goal | Endpoint |
| --- | --- |
| Review one document | `POST /v1/evaluate` |
| Analyze one observable rollout | `POST /v1/benchmark-rollout-analyses` |
| Discover the canonical GDPx contract | `GET /api/v3/gdpx/capabilities` |
| Submit a canonical draft or active evidence-catalog candidate | `POST /api/v3/gdpx-submissions` |
| Import a legacy workspace draft | `POST /api/v2/workspace-submissions` |

The v1 services return feedback only. V2 creates legacy drafts only. V3 is the canonical task-and-evidence workflow.

## Configure one API origin and key

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"
```

Use the same API origin for the v1 request and any subsequent v3 discovery. Do not infer v3 availability from `/v1/whoami` or a v2 capability response.

## Submit a document

Send one supported document as multipart form data:

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/v1/evaluate" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --form "file=@task-specification.md" \
  --output task-feedback.json
```

Use PDF, DOCX, Markdown, or JSON only when the endpoint advertises that media type. Do not send the complete task or evidence ZIP to this route.

## Interpret the response

The response may include:

- an aggregate document verdict;
- blocking findings;
- warnings;
- evidence citations into the submitted document; and
- suggested corrections.

Treat `ready_to_submit`, when present, as a verdict about the document only. It does not authorize a ZIP, prove the environment runs, validate rollout evidence, or add a task to the active evidence catalog.

Resolve each blocker in the source document. Then rerun the document review if useful.

## Continue to the real submission

After document review:

1. prepare the [partner source handoff or canonical bundle](/gdpx/benchmark-task-package);
2. fetch `GET /api/v3/gdpx/capabilities`;
3. follow the advertised schema, mode, adapter, and size limits; and
4. use the [v3 evaluation bundle flow](/gdpx/evaluation-bundle-upload) for canonical submission.

If you only need a legacy draft import, use the [v2 workspace flow](/gdpx/import-approved-tasks) when Standard Data explicitly directs you to it.

## Common errors

| Status | Meaning | Action |
| --- | --- | --- |
| `400` | Invalid request or unsupported document | Send one supported document |
| `401` | Missing or invalid API key | Supply a valid bearer key |
| `403` | Key lacks the required evaluation scope | Request the correct scope |
| `413` | Document exceeds the advertised limit | Reduce the document without removing required evidence |
| `422` | Document could not be evaluated under the request contract | Correct the reported field or file issue |
| `429` | Rate limit exceeded | Follow `Retry-After` |
| `5xx` | Service unavailable or evaluation failed | Retry only after checking service status |

Never treat an endpoint error as a task score.
