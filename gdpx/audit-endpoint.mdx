`POST /v1/evaluate` reviews one task specification or benchmark methodology document and returns findings and suggested fixes.

It does **not** inspect a Harbor directory, check whether `task.toml` exists on disk, build the environment, run the verifier, or validate a workspace ZIP. A missing file can be discussed only from the evidence you submit.

## Choose the endpoint

| Goal | Endpoint |
| --- | --- |
| Review one document | `POST /v1/evaluate` |
| Retrieve its feedback | `GET /v1/evaluations/{evaluation_id}` |
| Analyze one normalized attempt | [`POST /v1/benchmark-rollout-analyses`](/gdpx/benchmark-rollout-analysis) |
| Discover the API bundle contract | `GET /api/v3/gdpx/capabilities` |
| Submit a canonical draft or task-and-evidence bundle | [`POST /api/v3/gdpx-submissions`](/gdpx/evaluation-bundle-upload) |

The repository format is documented under [Task format](/gdpx/quickstart). Neither feedback endpoint imports that folder or approves a QC stage.

## Configure access

Use one origin and a key with `evaluations:write`. Retrieval requires `evaluations:read`.

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/v1/whoami"
```

Check the effective scopes. Successful authentication does not establish submission readiness.

## Prepare the document

Send one PDF, DOCX, Markdown, or JSON file, up to 10 MB decoded. Do not send a ZIP, raw rollout archive, or full repository.

You can submit the task instruction for an early review. For useful packaging and grading feedback, include the relevant runtime declaration, rubric, verifier behavior, and known-good evidence in the document. The service cannot discover files you did not provide.

| Option | Use |
| --- | --- |
| `declared_mode` | Set `benchmark` for benchmark tasks; other supported modes include `rl`, `sft`, `rlvr`, `rlhf`, `dpo`, `sdft`, `agentic`, and `both` |
| `verbosity` | `summary` or `full` |
| `checks_to_run` | `all` or selected named checks |
| `include_suggested_fixes` | Include proposed corrections |
| `end_target` | Record downstream intent; v1 does not enforce that profile |

Document feedback uses `guidelines_version: v14`. It is not the canonical submission gate. Resolve any `MODE_DECLARATION_CONFLICT` between the request and document.

## Submit a file

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/v1/evaluate" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --form "file=@task-specification.md" \
  --form 'options={"declared_mode":"benchmark","verbosity":"summary"}' \
  --output task-feedback.json
```

Multipart supports `.pdf`, `.docx`, `.md`, `.markdown`, and `.json`.

JSON transport uses `task_input.format`, `task_input.filename`, `task_input.content`, and `options`. Markdown and JSON content is UTF-8 text; PDF and DOCX content is base64. Use a JSON encoder rather than manually escaping a document. The [live OpenAPI](https://api.standarddata.io/openapi.json) defines the request fields.

## Read and retrieve feedback

Check `kind`: `task_spec` returns task/step feedback and priority findings; `benchmark_paper` returns methodology and stage findings.

Both include `evaluation_id`, `aggregate_verdict`, applied guidelines, model/latency metadata, and `canonical_submission` context. Summary mode retains up to ten priority findings for task specifications.

`aggregate_verdict.ready_to_submit` applies only to the reviewed document. It does not prove that a task runs, that its Harbor files exist, or that an unrelated ZIP is eligible.

Retrieve the stored result with the same tenant's authorized key:

```bash
EVALUATION_ID="$(jq -r '.evaluation_id' task-feedback.json)"

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/v1/evaluations/${EVALUATION_ID}" \
  --output task-feedback-retrieved.json
```

## Handle failures

| Status or finding | Action |
| --- | --- |
| `400` / `422` | Correct the reported transport, document, options, or schema fields |
| `401` / `403` | Check the key, expiry/revocation, and required scope |
| `413` | Reduce the document below the decoded-size limit |
| `429` | Follow `Retry-After` |
| `500` / `502` / `503` | Preserve the error details and follow retry guidance; escalate repeated failures |
| `EVALUATION_GRADER_UNAVAILABLE` | The grader did not complete; this is not evidence that the task itself failed |

Preserve the evaluation or request ID, stable error code, stage, retryability, details, and remediation when returned. Do not replace that information with a generic “Bad Gateway” message or count a degraded review as a clean result.

After fixing the findings, check the actual [task package](/gdpx/benchmark-task-package). For API submission, discover the live v3 capabilities and follow [API bundle upload](/gdpx/evaluation-bundle-upload).
