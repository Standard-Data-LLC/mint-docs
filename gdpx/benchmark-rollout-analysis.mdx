`POST /v1/benchmark-rollout-analyses` examines one normalized, observable attempt. Use it for a structured first pass on where a failure started and whether it is legitimate.

<Warning>
  This endpoint is optional and analysis-only. It does not store the rollout, create canonical evidence, pass a QC stage, or add evidence to the active evidence catalog. If you use it, retain the exact request and response.
</Warning>

## What the analysis answers

The analysis keeps three questions separate:

1. What did the verifier report?
2. What first went wrong in the observable attempt?
3. Is the result valid benchmark evidence, or did the task, verifier, runtime, provider, or orchestration fail?

A classification cannot replace the repeated-run evidence required for QC2 or the evaluation plan required for QC3.

## Prepare the request

Bind the request to one exact task revision, source run, and rollout. Give the endpoint:

- the task instruction and relevant agent-visible context;
- atomic rubric criteria and known-good evidence;
- the ordered observable trajectory and final output;
- verifier outcome, reward, threshold, per-test output, and verifier identity;
- environment, provider, and orchestration status;
- model, harness, budgets, usage, timeout, and stop reason; and
- stable evidence IDs for every quoted item.

Leave out private chain of thought, actual credentials, signed URLs, and provider-private payloads.

If the full retained evidence exceeds the endpoint's request limit, make a faithful analysis projection that preserves the first failure and every failed test. The complete source evidence still belongs in the canonical bundle. A smaller analysis request does not authorize truncated rollout evidence.

## Call the endpoint

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"

curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/v1/benchmark-rollout-analyses" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --data-binary @rollout-analysis-request.json \
  --output rollout-analysis-response.json
```

The request is synchronous. Follow the request contract returned by the service, not a cached example.

## Read the response

Along with the exact task and rollout identities, the response includes:

| Field | Meaning |
| --- | --- |
| `analysis_status` | `complete` or `needs_human_review` |
| `observed_verifier_outcome` | The verifier outcome from the request |
| `deep_swe_tag` | The closed failure category when the evidence supports one |
| `confusion_class` | The verifier disposition: TP, TN, FP, or FN |
| `failure_legitimacy` | Whether this was a valid model failure, non-model failure, invalid pass, passing rollout, or unresolved case |
| `failure_origin` | Model, prompt, verifier, environment, provider, orchestration, training data, triangulation, or unknown |
| `first_failure_locator` | The first grounded divergence |
| `evidence` | Citations to submitted observable evidence |
| `failing_tests` | Per-test root causes |
| `qc_recommendation` | Accept as evidence, repair and rerun, harden and rerun, or human review |
| `missing_inputs` | Evidence required before the result can be resolved |
| `input_fingerprint` / `output_fingerprint` | Hashes used to retain the analysis with the attempt |

`analysis_status: complete` means the endpoint finished its classification. It does not mean the task passed QC.

## Understand failure legitimacy

A failed attempt can count as a legitimate model failure only when:

- the task is solvable and sufficiently clear with the supplied context and tools;
- the instruction, rubric, tests, and verifier agree;
- the environment, provider, and orchestration are healthy;
- the model behavior caused the failure; and
- the evidence is complete enough to support the conclusion.

Common non-model origins include:

- broken or mismatched tests;
- hidden expectations not stated or discoverable;
- ambiguous instructions;
- unavailable tools or dependencies;
- provider or controller failures; and
- reward leakage or a cheated pass.

The category label alone is not enough to establish legitimacy.

## Apply the saturation rule

This analysis does not override GDPx difficulty review.

- A passing QC1 attempt proves construction, not difficulty.
- One failed attempt does not prove difficulty.
- If the QC1 model repeatedly passes or reaches the score ceiling, keep the task in QC1, harden or remove it, and rerun the new revision.
- Do not count a saturated smoke result as QC2 evidence.

See [QC2: Difficulty and reward integrity](/gdpx/benchmark-task-delivery#qc2-difficulty-and-reward-integrity).

## Handle human review

If the evidence cannot establish the first failure, solvability, verifier alignment, or runtime health, the service returns `needs_human_review` and names the missing inputs.

Add the missing observable evidence or record a qualified human review. An unresolved result cannot be recast as a legitimate model failure.

## Retain the analysis correctly

If you call the endpoint, keep these files beside the rollout:

```text
rollout-analysis-request.json
rollout-analysis-response.json
failure-analysis.md
```

Bind each file to the task, run, and rollout with its path, media type, byte size, and SHA-256. The readable summary should identify:

- the verifier outcome and score;
- the first observable failure;
- every affected criterion or test;
- the failure origin and evidence references;
- the endpoint's status, category, legitimacy decision, and recommendation;
- the request and response fingerprints; and
- unresolved inputs or required reruns.

These files are supporting artifacts. They do not replace `trajectory.atif.json`, `verifier.json`, `criterion-decisions.json`, native work products, or the reviewer-visible sections.

See [Canonical ZIP layout](/gdpx/evaluation-bundle-upload#canonical-zip-layout) and [Rollout viewer evidence](/gdpx/rollout-viewer-evidence).

## Errors

| Status | Meaning | Action |
| --- | --- | --- |
| `400` | Invalid content type or JSON | Send one valid JSON object |
| `401` | Missing or invalid API key | Supply a valid bearer key |
| `403` | Key lacks the analysis scope | Request the correct scope |
| `413` | Request exceeds the current limit | Create a faithful bounded projection; do not truncate canonical evidence |
| `422` | Schema or evidence binding failed | Correct the reported request errors |
| `429` | Rate limit exceeded | Follow `Retry-After` |
| `502` | Judge response failed validation | Retry once when appropriate, then escalate |
| `503` or `504` | Service unavailable or timed out | Retry after service recovery |
