---

`POST /v1/benchmark-rollout-analyses` analyzes one normalized attempt. It returns a cited failure classification and recommended repairs. It does not import evidence, advance QC, or certify a task.

## Prepare the attempt evidence

Select one result from `run.json` and its matching trace and artifacts. A run with several trials needs separate analysis requests.

Use the request schema in [live OpenAPI](https://api.standarddata.io/openapi.json), under `BenchmarkRolloutAnalysisRequest`. Supply:

- `task`: instruction, rubric, known-good evidence, and immutable identity;
- `rollout`: model identity, ordered observable events, final output, and usage;
- `verifier`: outcome, score, threshold, and per-test evidence;
- `runtime`: Oracle smoke, environment/provider/orchestration health, limits, and action definitions; and
- stable evidence IDs, with tool calls linked to their results.

The API requires a canonical `taskrev_<64 lowercase hex>` ID and task-content hash. Use the verified mapping for the exact task revision. If you only have source-system IDs, obtain that mapping from Standard Data; do not change an ID prefix or invent a hash to satisfy validation.

Your rubric weights may use another scale. If you supply the API's optional criterion `weight`, normalize it to the schema's 0–1 range using the actual scoring rule. Preserve the original aggregation and hard gates in the evidence.

## Keep the request bounded and safe

The request limit is 2 MiB, with at most 1.5 MiB of evidence text and further per-field limits. Send a faithful analysis projection that retains the first failure and every failed test—not a ZIP, raw `run.json`, or complete provider archive.

Exclude private reasoning, secrets, credentials, internal storage paths, signed URLs, and provider-private payloads, including values embedded in nested objects or schema keys.

The full observable source evidence still belongs with the attempt. A smaller API request does not make missing or truncated source evidence complete.

## Call the endpoint

Use a key with `evaluations:write`:

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"

curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/v1/benchmark-rollout-analyses" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --data-binary @rollout-analysis-request.json \
  --output rollout-analysis-response.json
```

The request is synchronous. Retain the exact request and response as supporting evidence bound to the source task, run, and attempt.

## Read the decision

| Fields | Meaning |
| --- | --- |
| `analysis_status`, `missing_inputs` | Complete classification or unresolved human review |
| `deep_swe_tag`, `confusion_class` | Failure category and verifier disposition |
| `failure_legitimacy`, `failure_origin` | Whether the result is valid, and whether the model or another system caused it |
| `first_failure_locator`, `evidence`, `failing_tests` | Cited first divergence and per-test root causes |
| `benchmark_fix`, `model_behavior_fix` | Task/verifier/infra repairs versus model mistakes |
| `qc_recommendation` | Accept as evidence, repair and rerun, harden and rerun, or human review |
| `input_fingerprint`, `output_fingerprint` | Bind the analysis to its inputs and output |

A category alone does not establish legitimacy. A model failure needs a solvable task, passing Oracle smoke, aligned verification, healthy runtime, and observable evidence explaining the failed tests.

`TRIAL_INCOMPLETE` additionally requires genuine model-caused exhaustion under adequate declared limits. A mechanical timeout or missing budget is not enough.

A legitimate pass remains a pass. If repeated attempts saturate the task, harden or remove it and review the new revision; do not relabel success as a failure. See [QC stages](/qc-stages-for-benchmark).

## Handle errors

| Status | Action |
| --- | --- |
| `400` / `422` | Correct the request, identity mapping, evidence links, or reported fields |
| `401` / `403` | Check the key and `evaluations:write` scope |
| `413` | Reduce the analysis projection without discarding required source evidence |
| `429` | Follow `Retry-After` |
| `502` | Inspect the reason: judge output or evidence validation did not complete |
| `503` / `504` | Follow the returned retry guidance for service or provider recovery |

Retain `request_id`, error code, `reason_code`, `failure_stage`, and `retryable` when returned. A service failure with `task_grade_issued: false` is not a failed task grade. Do not retry indefinitely or turn the error into a model failure.

An unresolved `needs_human_review` result also cannot be counted as a legitimate model failure. Supply the missing observable evidence or obtain a qualified review.
