## Partner delivery and Standard Data review

Submit the canonical task bundle above, or a batch archive that maps to it without requiring us to invent missing facts. You are responsible for the source assets, rights and sanitization notes, rubric rationale, tool definitions, and calibration artifacts.

### QC1: Integrity in construction

Run one smoke rollout on the exact task revision with GPT-5.6 Luna. QC1 checks that the environment builds and resets, tools and source files are available, and the verifier returns a valid score. It does not establish difficulty.

Retain the complete prompt, observable trajectory, final answer or work product, six forensic evidence sections, criterion decisions, and score reconciliation described in [Rollout viewer evidence](/gdpx/rollout-viewer-evidence). Bind the canonical package to a valid `PUBLICATION_AUTHORITY.json`; this is the uploaded publication declaration, not the operator rights grant. Technical QC evidence alone does not authorize catalog membership.

Run the smoke through the approved managed execution path. Audit retains the runtime receipt and creates a separate operator-authenticated managed-execution approval only when it matches the exact task content, full workspace inventory, run, rollout, and canonical evidence bytes. An uploader-supplied receipt or validation claim remains archive-only. Fix task, tool, source, verifier, evidence-capture, authority, or execution defects and repeat the smoke test. A task stays in QC1 until one clean current-revision run shows that failures come from model behavior rather than broken construction.

You may use [rollout analysis](/gdpx/benchmark-rollout-analysis) to separate a model failure from a task, verifier, environment, provider, or orchestration defect. Its recommendation supports review but does not move the task out of QC1.

### QC2: Difficulty and reward integrity

Run repeated rollouts in the task's native frontier harness. Check that rewards are stable and interpretable, successful runs solved the intended task, and failed runs are legitimate model failures. Review reward hacking, leakage, grader bias, false positives, and false negatives.

A task advances only when the signal is non-saturated. If Luna already passes nearly every run or scores at the ceiling, keep the task in QC1, harden or drop it, and rerun the current revision. A saturated smoke result is not QC2 evidence.

One `legitimate_model_failure` result does not establish QC2. Review the repeated current-revision rollout set for stable, non-saturated difficulty and reward integrity.

### QC3: Benchmark evaluation

<Info>
  Do not start QC3 until QC1 and QC2 are complete.
</Info>

Run 16 completed subject rollouts per task for each model–harness pairing in the current evaluation matrix. Standard Data provides the matrix with the evaluation window. Use the listed native harness and pinned task revision. Extra models and alternate harnesses do not replace a required pairing.

An attempt counts only when it has a final reward, a pass threshold, a `passed` or `failed` outcome, and the required artifacts. Infrastructure failures and retries do not count toward 16. Keep hinted runs, Oracle runs, and calibration anchors out of the subject set.

The required artifacts must satisfy the [reviewer-visible rollout evidence contract](/gdpx/benchmark-task-package#preserve-reviewer-visible-rollout-evidence). Metadata-only rows and provider references do not count as completed attempts.

#### Record results in `TASK.json`

`TASK.json` is the Standard Data intake manifest shipped with the Harbor task. Put it beside `task.toml` under `tasks/<task_name>/`. Its `rollouts` field indexes the result set. Full traces, rewards, and failure analyses stay under the root-level `trajectory/` directory.

Fetch the authoritative publication contract from `GET /api/v3/gdpx/schemas/review-bundle` with your API key. The v3 capability response links to the same route and controls adapter availability. The current v1.1 `task_and_evidence` contract accepts 1–100 unique tasks per ZIP, with exactly one evaluation and one QC1 rollout for each task. Task, revision, logical-task, run, and rollout identities must be unique as required by the live schema, and the set imports atomically. There is no supported `/api/v2/intake-schemas/task-json` endpoint.

Add `rollouts` to the existing task-taxonomy manifest; do not remove the identity, construct, runtime, scoring, horizon, evidence, or provenance fields described above. The shortened example below shows the rollout extension.

```json
    "harbor_version": "1.4",
    "private_reasoning_omitted": true,
    "models": {
      "<model-key>": {
        "model": "<model-name>",
        "provider": "<provider>",
        "provider_model_id": "<provider-model-id>",
        "execution_mode": "api",
        "harness": "Claude Code",
        "harness_version": "<pinned-version>",
        "run_config": {
          "prompt": { "prompt_sha256": "sha256:<64-lowercase-hex>" },
          "tool_config_sha256": "sha256:<64-lowercase-hex>",
          "sampling": { "temperature": 0 },
          "context_policy": "<pinned-policy>",
          "turn_budget": 100,
          "timeout_seconds": 3600,
          "retry_policy": { "max_attempts": 2, "backoff_seconds": 5 }
        },

          {
            "rollout_id": "<stable-id>",
            "ordinal": 1,
            "kind": "subject",
            "status": "failed",
            "reward": 0,

            "wall_time_seconds": 842,
            "usage": { "prompt_tokens": 12500, "completion_tokens": 4200 },
            "cost_usd": 0.42,
            "artifacts": {
              "trajectory": { "path": "trajectory/<task_name>/<model-key>/1/trajectory.json", "sha256": "sha256:<64-lowercase-hex>", "size_bytes": 123456, "media_type": "application/json" },
              "reward": { "path": "trajectory/<task_name>/<model-key>/1/reward.json", "sha256": "sha256:<64-lowercase-hex>", "size_bytes": 456, "media_type": "application/json" },
              "failure_analysis": { "path": "trajectory/<task_name>/<model-key>/1/failure_analysis/failure_analysis.md", "sha256": "sha256:<64-lowercase-hex>", "size_bytes": 2345, "media_type": "text/markdown" }
            }
          }
        ]
      }

```

Include every model key in the current evaluation matrix and put exactly 16 completed `subject` attempts in each one, with ordinals `1` through `16`. Use one pass threshold across the task. Reference, hinted, and infrastructure attempts must use a different `kind` and do not count toward the subject set.

Pin the prompt, tool configuration, sampling, context policy, budget, timeout, and retry policy in `run_config`. Every digest uses the `sha256:<64-lowercase-hex>` form, and every artifact path is relative to the batch root. A failed attempt needs `failure_analysis`; a passing attempt does not. Every attempt needs the complete v3 rollout evidence and criterion ledger. Never include private reasoning, actual or live credentials, secret values, or raw provider events. An isolated synthetic fixture is retained only through the [internal-QA exact-byte attestation path](/gdpx/evaluation-bundle-upload#internal-qa-exact-byte-fixture-retention).

Every artifact path must resolve to the exact uploaded bytes and match its declared hash, size, and media type. The trajectory must expose the observable execution, and generated work products must be included as inspectable native artifacts. IDs, scores, and aggregate statistics are indexes and summaries, not rollout evidence.

Use `gdpx-task/1.1.0` for canonical publication. Inventory every workspace file with its normalized path, SHA-256, byte size, media type, artifact kind, and visibility. Compute `environment.workspace_inventory_sha256` over that sorted inventory. Compute `task_content_sha256` over the complete canonical task graph as defined by the fetched schema. `RUN.json` must bind the same workspace inventory. Audit rejects an omitted file or any path, hash, size, media-type, kind, or visibility mismatch.

### Standardized Harbor runtime

Run QC3 on the standardized Harbor runtime. Bind every result to the exact task bytes, environment digest, Harbor release, harness release, and run configuration. Custom reward or environment-interaction extensions are fine when they run inside Harbor and are fully declared. They do not replace a required model harness. Replace custom agents or runtimes with the standard runnable agent before QC3; results from an incompatible runtime do not count.

`TASK.json` is task-local intake metadata, not an agent file. Never mount it, `trajectory/`, `docs/`, tests, solutions, or hidden grading material into the agent runtime.

A trusted-runtime attestation rejection before launch is an infrastructure attempt, not a failed subject rollout. Runtime success requires a completed one-shot privilege attestation and an independently validated canonical sidecar that matches frame A before the launch gate opens. Empty stdout and stderr alone do not prove success. Empty stderr may omit the marker only when that sidecar/frame-A check passes; non-empty stderr requires one well-formed, first, byte-identical marker.

Retain only its stable reason (`missing_marker`, `duplicate_marker`, `marker_not_first`, `malformed_marker`, `missing_sidecar`, `malformed_sidecar`, `mismatched_sidecar_a`, `controller_timeout`, or `controller_terminated`) and bounded marker, stream, timing, return-code, and sidecar validity metadata. Do not retain raw stdout, stderr, marker values, or sidecar bytes. It produces no score and receives no QC credit. These rules do not claim that a particular runtime build has passed a live canary.

### QC4: Analysis and normalization

We review the full rollout set, investigate false positives and false negatives, and run extra harness checks when they answer a real question. This pass determines final inclusion. We normalize accepted tasks and evidence after that decision.

If experts review rollouts during development, keep a simple log in `samples/`. Record the reviewer, task revision, decision, and rationale so later agreement analysis can use the original review data.

## Partner checklist

- A qualified practitioner can solve the task using only the supplied context and tools.
- Both kickoffs ask for the same job.
- Native inputs open, and the environment resets cleanly.
- The reference output passes; known-bad outputs fail for the intended reason.
- Deterministic checks cover everything code can settle.
- Every judge criterion is atomic and cites observable evidence.
- Every rollout has a final answer or primary work product, all six forensic sections, and criterion-level score reconciliation.
- The exact revision has a task-bound uploaded publication declaration with the applicable rights basis and owner intent.
- Standard Data's current immutable rights grant and authority head match that exact declaration, task content, workspace inventory, and source delivery.
- The qualifying run has an operator-authenticated managed-execution approval for the exact retained receipt and evidence.
- Alternate valid methods are not penalized.
- Agent-visible, grader-only, and gold files are isolated correctly.
- Source, rights, sanitization, and overlap-risk metadata are complete.

Use the [audit endpoint](/gdpx/audit-endpoint) for non-canonical document feedback while authoring. A clean document audit never authorizes a ZIP. When the GDPx capability endpoint reports `ready`, [upload the evaluation bundle](/gdpx/evaluation-bundle-upload); the exact archive must complete managed execution, approval, and current-policy readiness before it can enter Wilderness.
