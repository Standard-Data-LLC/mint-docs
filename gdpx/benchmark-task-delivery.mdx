Partners deliver complete task source, rights information, verifier logic, and any native evidence. Standard Data owns managed QC execution, benchmark review, normalization, and the final inclusion decision.

## Responsibilities

| Partner | Standard Data |
| --- | --- |
| Deliver the exact runnable task and source material | Confirm the source layout or adapter |
| Explain the intended work, task family, and rubric | Normalize accepted source into the canonical GDPx contract |
| Provide rights, provenance, and sanitization information | Run or verify the managed QC1 smoke |
| Preserve any supplied trajectories, verifier output, and work products | Review difficulty, reward integrity, and failure causes |
| Correct task, environment, or verifier defects found in review | Run the approved evaluation matrix and decide inclusion |

There is no public endpoint for launching or approving managed QC1. A partner-supplied Harbor run or provider export is useful preflight evidence, but it does not approve itself or automatically advance a QC stage.

## Before QC: runnable readiness

A task is ready to enter QC when:

- the exact environment builds and resets;
- all required source files and tools are available;
- the verifier runs and returns interpretable output;
- a known-good solution passes when one can reasonably be represented, or an equivalent solvability check passes;
- a no-op, known-bad output, or equivalent negative control fails; and
- the task, verifier, and evidence contain no secrets or inaccessible dependencies.

This is a pre-QC readiness state. Do not call it QC0, Stage 0, or G0. The build check may be labeled G0 inside an authoring checklist, but that label is not a benchmark stage.

## The four GDPx review stages

### QC1: Construction integrity

Standard Data runs or verifies one qualifying managed smoke attempt on the exact frozen task revision. Failed or rejected construction attempts may precede it and do not count. QC1 asks whether the environment, tools, source files, reset behavior, verifier, and evidence capture work together.

The attempt must preserve the prompt, observable trajectory, final answer and work products, verifier output, criterion decisions, and score reconciliation. A partner may supply an existing attempt for diagnosis, but the task remains in QC1 until Standard Data validates a qualifying managed attempt on the same revision.

QC1 does not establish difficulty. A clean pass proves that the task runs; it does not prove that the task is challenging enough for the benchmark.

### QC2: Difficulty and reward integrity

Standard Data reviews repeated current-revision attempts in the native harness. The review asks:

- Is the signal non-saturated and useful?
- Do successful attempts solve the intended task?
- Are failed attempts legitimate model failures?
- Does the verifier resist leakage and reward hacking?
- Are false positives, false negatives, and partial-credit decisions acceptable?

If the QC1 model repeatedly passes or reaches the score ceiling, the task does not pass QC2. Harden the task or remove it, then rerun the new revision. Do not promote a saturated task merely because its environment works.

One failed attempt also does not prove difficulty. QC2 is a repeated-run judgment about the task and reward signal.

### QC3: Benchmark evaluation

After QC1 and QC2, freeze the task revision and run the written model–harness matrix. The current default is 16 completed subject attempts per task for each required pairing unless Standard Data issues a different evaluation plan for that campaign.

An attempt counts only when it has:

- the exact frozen task and runtime configuration;
- a final reward, threshold, and pass/fail outcome;
- complete reviewer-visible evidence;
- all required native work products; and
- no infrastructure or provider failure that invalidates the attempt.

Retries, setup failures, Oracle runs, hinted runs, and calibration probes do not count toward the subject total.

<Info>
  QC3 is an evaluation corpus, not one canonical task file. Do not put 16 attempts in `TASK.json`. Standard Data owns QC3 ingestion and campaign mapping. Partners should preserve the complete native corpus and should not submit individual QC3 attempts through `evidence_only` unless a Standard Data operator provides the target revision and admission plan. The current API does not natively label a run as QC3.
</Info>

### QC4: Release review

Standard Data reviews the complete evaluation set, checks failure modes and scoring behavior, resolves material anomalies, and normalizes accepted evidence for release. QC4 ends with an explicit inclusion, rework, or removal decision.

## API status versus program status

The current v3 backend enforces the requirements for entry into the active evidence catalog around canonical task evidence and managed QC1. QC2, QC3, and QC4 are program review stages tracked separately.

Therefore:

- `review_ready` does not, by itself, mean QC2 through QC4 are complete;
- an active evidence-catalog record does not mean the task is in the released GDPx benchmark; and
- a partner-supplied trajectory does not count as a passed QC stage until Standard Data reviews it under the applicable stage.

Use the benchmark tracker or written review record for the four-stage status. Use the API for immutable task and rollout evidence.

## Failure analysis

Every failed attempt in the delivered or evaluated corpus needs a readable, evidence-grounded failure-analysis summary. It must identify:

- the first observable failure;
- the affected test or rubric criterion;
- whether the origin is the model, task, verifier, environment, provider, or orchestration;
- the exact trajectory, tool, test, or artifact evidence supporting that conclusion;
- whether the task remained solvable with the supplied context and tools; and
- any required repair and rerun.

The [rollout-analysis endpoint](/gdpx/benchmark-rollout-analysis) is optional. Use it for a structured first pass when the failure origin is unclear. Its recommendation is evidence for review, not a QC-stage decision.

## Submission counts versus rollout counts

Keep these concepts separate:

| Concept | Count |
| --- | --- |
| Partner source handoff | May contain the complete native rollout corpus |
| v3 `task_and_evidence` ZIP | One evaluation and one rollout for each unique task in that ZIP |
| v3 `evidence_only` ZIP | One rollout candidate for one retained task revision |
| QC3 evaluation corpus | The number of completed attempts required by the written evaluation matrix |

An `evidence_only` submission can supply the first QC1 attempt for an exact retained canonical Audit draft. For an already retained revision, it freezes a later attempt candidate that requires separate operator admission and leaves the qualifying QC1 anchor unchanged. The live schema and submission state determine which case applies.

## Final handoff checklist

Before handoff:

- freeze the exact task revision and file inventory;
- include the runnable environment, verifier, and calibration evidence;
- include rights, provenance, sanitization, and overlap-risk notes;
- retain every supplied attempt's observable trajectory, outputs, work products, verifier evidence, and grading;
- add an evidence-grounded summary for every failed attempt;
- identify incomplete or truncated source evidence plainly;
- record the ZIP size and SHA-256; and
- state whether the package is a partner source handoff or a canonical v3 bundle.

See [Task packaging](/gdpx/benchmark-task-package) for the two layouts and [Evaluation bundle upload](/gdpx/evaluation-bundle-upload) for direct API submission.
