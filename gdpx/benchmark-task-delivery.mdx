Deliver one folder per task, following the [task layout](/gdpx/quickstart#task-layout). Group batches by domain and keep each task's runtime files and recorded evidence together.

## Responsibilities

| Partner | Standard Data |
| --- | --- |
| Provide the instruction, runtime, starting data, verifier, and reference material | Review construction, solvability, scoring, and difficulty |
| Explain source rights, task family, and dependencies | Confirm identity mappings and any API normalization |
| Preserve supplied runs, traces, native artifacts, and failure analyses | Run or verify the required evaluation plan and make release decisions |
| Repair defects and identify changed bytes | Review the new revision and accepted evidence |

Do not fabricate task identities, run records, scores, or execution receipts. If your source does not yet have issued IDs, identify it as a new task and let intake assign them.

## Handoff checklist

- Pin the task revision and source package hash.
- Include `task.toml`, instructions, environment, tests, reference material, and any declared steps.
- Identify private images, external data, tools, rights, and required runtime configuration.
- Keep Oracle/no-op checks in `qc/` and model attempts in `rollouts/`.
- Preserve every supplied attempt's record, trace, verifier output, and native work products.
- Include an evidence-grounded explanation for failed attempts used in review.
- Include every required artifact's actual bytes, or mark the handoff incomplete.
- Remove secrets and private reasoning; keep protected grading material out of the agent environment.

A file inventory or `status: draft` is not a passing QC result. Check actual trial evidence and the review decision.

## Choose the delivery path

**Source delivery:** hand over the task folders and complete evidence through the agreed channel. Preserve native filenames and source provenance.

**Direct API delivery:** build a separate canonical bundle using [API bundle upload](/gdpx/evaluation-bundle-upload). A task-folder ZIP does not satisfy that contract by itself.

For multi-run campaigns, retain all current-revision evidence in the source layout. The API's one-rollout-per-task-per-bundle limit does not limit what you retain with the task.

## Review and release

Follow the four [QC stages](/qc-stages-for-benchmark). Upload success, retained evidence, and API `review_ready` each describe a technical state—not completion of all program reviews.

When a task changes, identify the new revision and rerun affected checks. Never overwrite earlier evidence or relabel it as a run of the new task.
