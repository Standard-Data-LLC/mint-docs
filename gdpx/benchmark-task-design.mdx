## Define the work

Start with the capability, not the file type. Name the practitioner, the decision or state change they own, and the errors that matter.

| Weak | Better |
| --- | --- |
| Produce a spreadsheet | Reconcile conflicting operating data and leave a decision-ready forecast with traceable assumptions |
| Summarize the documents | Triage an escalation across product, contract, and account history, then recommend the next action under policy |
| Use the tools correctly | Update a live operating artifact without breaking formulas or downstream dependencies |

A task family should make clear who does the work, what outcome matters, and what a strong practitioner would notice. Renaming companies or changing numbers does not create a new family.

## Draft the kickoff

During authoring, write the same job two ways:

1. `kickoff.md`: the unstructured message a manager, client, or colleague would actually send.
2. `kickoff_structured.md`: the role, objective, constraints, and deliverable stated directly.

Compare the drafts to see whether the task stays realistic without becoming underspecified. Before execution, choose one exact prompt for the agent. Keep the other as supporting material rather than mounting two competing instructions in the runtime.

The real-world version can rely on ordinary practitioner judgment. Every private policy, definition, and source fact must still be discoverable in the environment.

Good ambiguity makes the model recover context. Bad ambiguity makes the task unsolvable.

## Build the environment

Give the agent native files and realistic state. A prose description is not a substitute for the workbook, document, codebase, CAD file, or system record the job actually uses.

For stateful or editable work, ship:

- the starting state and expected final state;
- intended changes and forbidden side effects;
- reset behavior between rollouts; and
- reopen, render, formula, executable, or diff checks that match the artifact.

The action space is a coding agent with provisioned CLI tools. List every tool and include its definition and skill documentation. Convert computer-use workflows into tool calls before submission.

## Grade observable work

Use deterministic checks where code can settle the answer: values, schemas, formulas, compilation, geometry, state transitions, reconciliations, and artifact integrity. Use a judge for evidence-based recommendations, prioritization, material contradictions, and caveats that require practitioner judgment.

Each rubric criterion needs:

- a stable ID and one independently gradable claim;
- an aggregation role, a weight when the aggregation uses weights, and a failure-mode tag;
- the observable evidence required to pass; and
- one aggregation rule for the task.

Report one reproducible numeric score and derive the pass/fail outcome from the declared threshold. Keep deterministic and judge contributions separate in the reward ledger.

Do not grade private reasoning or one preferred workflow. Alternate valid methods should pass.

## Calibrate the verifier

Before cross-model runs, include a practitioner reference output and a known-bad output or equivalent negative control. If the task uses partial credit or a judge, add a partial-credit anchor. State the expected per-criterion result for every anchor.

Try to fool the verifier. Change the response length, order, and formatting without changing the substance; the score should stay stable. Add plausible but irrelevant detail; the score should not improve.

False positives inflate measured capability, so they are more damaging than false negatives. A benchmark item is not ready just because its verifier agrees with the author.

## Recommended: calibrate difficulty

When you make a difficulty claim, prefer at least three model tiers and enough independent rollouts to estimate pass@1 and criterion-level behavior. Whatever calibration envelope you use, pin the model, harness, prompts, tools, sampling settings, turn budget, timeout, judge version, context policy, and retry policy for every supplied rollout.

Read mean rubric score and per-criterion pass rates alongside pass@1. A zero-pass item is unsolved at current capability; that alone does not prove it is difficult or broken. Before calling it non-broken or suitable for its intended use, gather this evidence when practical:

- a qualified practitioner can solve it with the exact context and tools;
- the practitioner output passes every applicable verifier component;
- the environment is reliable;
- at least one model shows meaningful partial progress, or the task is explicitly beyond frontier; and
- the verifier handles the known-good and negative controls correctly, plus partial-credit anchors when applicable.

If every model earns zero or near-zero partial credit, consider splitting or reworking the task. Items above roughly 50% pass@1 can serve as anchors, but they generally should not dominate the benchmark.
