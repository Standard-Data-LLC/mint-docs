## Define the job

Name the practitioner, the decision or state change they own, and the errors that matter. “Produce a spreadsheet” is a file request; “reconcile conflicting operating data and leave a forecast with traceable assumptions” is a task.

A new company name or different numbers do not create a new task family.

## Write the instruction

Put the runtime brief in `instruction.md`: the outcome, constraints, available context, and deliverables. Use the voice of a manager, client, or colleague.

Draft alternatives can help during authoring, but they are not extra required runtime files. For a multi-step task, keep the step-specific briefs and order declared in `task.toml`.

Let the agent exercise practitioner judgment. Make every private policy, definition, and source fact needed to solve the task discoverable. Do not hide required behavior only in the verifier.

## Build realistic starting state

Provide native files and tools, not prose descriptions of them. Declare resource limits, network policy, dependencies, reset behavior, and artifact capture in the runtime configuration.

For editable or stateful work, specify the intended changes and forbidden side effects. Check that work products reopen, render, calculate, compile, or execute as appropriate.

Keep the Oracle, hidden tests, grading credentials, and previous attempts outside the agent's access. Document any external service or data dependency needed to reproduce the run.

## Grade observable work

Use deterministic checks for values, schemas, formulas, compilation, geometry, state transitions, and artifact integrity. Use a judge only where practitioner judgment is needed.

Each criterion needs:

- a stable ID and one independently gradable claim;
- an aggregation role and weight when applicable;
- observable passing evidence and an explainable failure condition; and
- any dependency, threshold, or hard gate.

Reconcile the final score to the declared rule. Keep judge and deterministic contributions distinguishable. Raw weights need not sum to one if the verifier explicitly normalizes them; use its actual formula.

Accept alternative valid methods. Do not grade private reasoning, response length, or a preferred workflow instead of the requested outcome.

## Calibrate before claiming difficulty

Require a passing known-good check and a failing no-op or known-bad control. Add partial-credit anchors when partial credit or a judge is used. A file named “Oracle” is not proof that it passes.

Test irrelevant detail, reordered content, alternate valid answers, and plausible shortcuts. The verifier should stay stable when substance is unchanged and reject reward hacking.

Use the campaign's pinned model–harness plan for difficulty claims. Inspect criterion-level progress as well as pass rates. Retain zero-pass tasks only when solvability and verifier reliability are established. Separate easier calibration anchors from core items.
