Evaluate the exact bytes you plan to deliver. Any change to the instruction, environment, rubric, verifier, or source material creates a new revision, so rerun the applicable checks.

## Authoring checks

Run these checks before the four benchmark QC stages.

| Check | Expected result | Requirement |
| --- | --- | --- |
| Build and reset | The environment builds from delivered files and returns to a clean starting state | Required before QC1 |
| Known-good solution | The reference output receives the intended passing score | Required when a reasonable reference can be supplied; otherwise document the equivalent solvability check |
| No-op or known-bad output | Empty, irrelevant, or clearly wrong work fails | Required when applicable; otherwise document the equivalent negative control |

Authoring teams may call them G0, G1, and G2. Those are authoring checks, not QC0–QC2 or tracker stages.

For a direct GDPx Harbor delivery, the verifier writes `/logs/verifier/reward.json`. A capability-advertised adapter may accept and normalize its documented native verifier output. The canonical record must still include verifier evidence and criterion decisions that reproduce the score.

## Calibrate the verifier

Use deterministic checks wherever code can settle the question. Reserve a judge for criteria that require practitioner judgment.

For every rubric criterion:

- state one independently gradable claim;
- identify the observable evidence needed to pass;
- record the weight only when the aggregation rule uses weights;
- define dependencies or hard gates explicitly; and
- make the final numeric score and threshold-derived pass/fail outcome reproducible.

For weighted aggregation, the weights must sum to one. Unweighted and custom aggregation rules need their own deterministic reconciliation.

Calibrate against a known-good output and a known-bad output or equivalent negative control. If the task uses partial credit or a judge, add a partial-credit anchor. Then vary the wording and formatting without changing the substance: the score should stay stable. Add irrelevant detail: the score should not improve.

## Calibrate difficulty

Follow the written evaluation plan for target model tiers, harnesses, and attempt counts. GDPx does not use one universal pass-rate band for every task.

Core benchmark items should separate performance at the intended frontier. Easier items can serve as anchors. Keep a zero-pass task only when it is demonstrably solvable and its criterion-level scores still provide useful signal.

Before you make a difficulty claim, pin:

- model and provider revision;
- harness and harness version;
- prompt and tool configuration;
- sampling, context, budget, timeout, and retry policy;
- environment and verifier versions; and
- task-content and workspace-inventory identities.

QC3 attempt counts are defined on [Partner delivery](/gdpx/benchmark-task-delivery#qc3-benchmark-evaluation). Do not add the QC3 corpus to canonical `TASK.json`.

## Analyze every failed attempt

Every failed attempt used in review needs a readable failure analysis grounded in the retained evidence.

Include:

- the exact task, run, and rollout identity;
- the first observable failure;
- each affected test or rubric criterion;
- exact trajectory, tool, test, or artifact references;
- the failure origin: model, task, verifier, environment, provider, or orchestration;
- whether a qualified practitioner could solve the task with the same context and tools;
- confidence and any unresolved ambiguity; and
- the smallest repair and required rerun, if applicable.

For an optional structured first pass, use [Analyze a benchmark rollout](/gdpx/benchmark-rollout-analysis). Its response is not a QC decision. If you call it, keep the exact request, response, citations, and fingerprints with the same attempt.

<Warning>
  Never request, infer, retain, or expose private chain of thought. Base the analysis on observable messages, tool activity, state changes, artifacts, and verifier output.
</Warning>

## Use hints only as diagnostic probes

A hint can test a suspected failure cause, but it must not reveal the solution.

1. Identify the first likely failure from observable evidence.
2. Write a hint that names the dimension to reconsider without naming the answer.
3. Rerun the same pinned envelope.
4. Record the hint, rationale, result, and interpretation.

Hinted attempts are diagnostic only. They do not count toward the unhinted subject total.

## Review reward integrity

Inspect both passing and failed attempts. A suspicious pass may reveal:

- test or verifier modification;
- hardcoded expected outputs;
- reward-file manipulation;
- leakage from hidden material;
- a pass without completing the intended work; or
- a judge that rewards style instead of substance.

Keep confirmed exploits as evidence, exclude them from reported success rates, repair the verifier, and rerun the new revision.

## Report distributions

For each task or batch, report:

1. the failure taxonomy and review method;
2. counts by failure origin and model;
3. unresolved or human-review cases;
4. reward-integrity findings and exclusions; and
5. known limits of the evidence.

Leave ambiguous evidence unresolved rather than forcing it into a model-failure category.

## Review the correct package

### Partner source handoff

Check that:

- task identities map cleanly to native evidence;
- every environment is reproducible and resettable;
- each supplied attempt includes complete observable evidence and native work products;
- each failed attempt has a failure-analysis summary;
- source, rights, and sanitization information is present; and
- the agreed adapter is confirmed before changing the source layout.

### Canonical v3 bundle

Check that:

- the bundle follows the live capability response and linked schema;
- canonical `TASK.json` contains no `rollouts` field;
- each workspace and evidence file is inventoried and hash-bound;
- each v1.1 `task_and_evidence` ZIP contains only one evaluation and one rollout per unique task;
- for the same byte-identical retained canonical revision, `evidence_only` may retain one later attempt candidate only under operator direction; it requires separate operator admission and does not replace the qualifying QC1 anchor;
- every criterion has exactly one decision; and
- the reported and calculated scores reconcile.

See [Task packaging](/gdpx/benchmark-task-package) for the format boundary and [Evaluation bundle upload](/gdpx/evaluation-bundle-upload) for the canonical API contract.
