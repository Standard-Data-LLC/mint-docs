Evaluate the exact task bytes you plan to deliver. Rerun affected checks after any change to the instruction, environment, source data, rubric, or verifier.

## Validate construction

| Check | Required evidence |
| --- | --- |
| Build and reset | The environment starts with the intended tools and files and returns to a clean state |
| Oracle/reference | A known-good output receives the intended passing result |
| Negative control | No-op or known-bad work fails for the expected reason |

Keep these runs under `qc/<run-id>/`. A documented equivalent solvability check can cover a task without an executable Oracle; do not label a placeholder or unexecuted reference as a passing Oracle.

Preserve the verifier's native output. Current packages use `reward.txt`, `reward.json`, and supporting grader files. Follow that package's `tests/test.sh` and runtime contract instead of renaming reward files.

## Read the attempt, not just the run status

Use `run.json.results` to find individual outcomes, roles, scores, and trace references. A run marked `failed` may contain a scored task failure, a voided trial, or a runtime problem.

For each attempt, check:

- the run's `task_revision_id` against the task's exported `revision_id`;
- the model and harness recorded in the run, not inferred from a folder label;
- its attempt/role/trial identity and referenced trace;
- verifier completion, score, threshold, and hard gates; and
- native artifacts and any truncation or missing-evidence markers.

A grader crash, provider error, or setup failure is not a scored model failure. Keep it as a diagnostic and exclude it from subject success rates.

## Analyze failures

Every failed attempt used in review needs an evidence-grounded explanation:

1. Identify the first observable divergence and affected criteria or tests.
2. Cite the exact trace, tool result, verifier output, or work product.
3. Separate model behavior from task, verifier, environment, provider, and orchestration defects.
4. Check solvability with the same context and tools.
5. State uncertainty, required repair, and what must be rerun.

Retain the analysis with that attempt. The [rollout-analysis endpoint](/gdpx/benchmark-rollout-analysis) is an optional structured first pass, not a QC decision. Keep its request, response, and fingerprints if you use it.

## Check reward integrity

Inspect passes as well as failures. Look for leaked answers, test edits, hardcoded outputs, reward-file manipulation, and judges that reward style over substance.

Retain confirmed exploits, exclude invalid passes from success rates, repair the verifier, and rerun the new revision. Do not change the scoring rule after seeing results without recording a new revision.

Hints are diagnostic only: name a dimension to reconsider without revealing the answer, record the hint and outcome, and keep that run separate from unhinted subject attempts.

## Report distributions

Report counts by model–harness pair and failure origin, along with valid attempts, exclusions, unresolved cases, and reward-integrity findings.

Do not count `qc/` baselines, hints, duplicate retries, or invalid execution attempts as subject rollouts. A retried attempt counts only if it independently meets the campaign's validity rules.

Use [QC stages](/qc-stages-for-benchmark) for the evaluation plan and [Rollout evidence](/gdpx/rollout-viewer-evidence) for completeness checks. The number of folders in the repository does not establish sample size or pass@k.
