Use the [task layout](/gdpx/quickstart#task-layout): one folder per task, grouped by domain for a batch. Keep each task's filenames and supporting directories intact.

## Runtime files

| File or directory | Requirement |
| --- | --- |
| `task.toml` | Declare the runtime, resources, timeouts, network policy, and task metadata |
| `instruction.md` | State the agent's job, constraints, and deliverables |
| `environment/` | Preserve the build recipe or pinned image configuration, tools, and starting data |
| `tests/test.sh` | Run the verifier and retain its reward and explanatory output |
| `solution/` | Preserve the reference implementation, artifacts, or documented reference path |
| `steps/` | Preserve step instructions, workdir inputs, tests, and reference files when declared in `task.toml` |

Use one runtime instruction for a single-step task. For a multi-step task, preserve the declared order, state handoff, per-step overrides, and reward aggregation. Do not merge its prompts or grade every step as an independent task.

Harbor Oracle execution uses `solution/solve.sh`. Some retained packages document a different reference entry point; follow the task's own instructions. A reference artifact alone does not make the Oracle agent runnable, and a structure-only placeholder does not prove solvability.

## Keep protected material out of the agent environment

Mount only the instruction, starting files, and permitted tools for the model attempt. Keep hidden tests, Oracle material, prior answers, `rollouts/`, and `qc/` out of that environment.

Do not mount the full delivery folder into the agent environment. Enforce separation through the container, filesystem permissions, and verifier configuration. Keep verifier credentials server-side.

## Preserve task identity

If supplied, preserve the source `TASK.json` and its task/revision identity, provenance, and associated run IDs. Match each `run.json.task_revision_id` to that task's recorded revision. A display name or folder name is not a server ID.

For a new task, provide its source, rights, task family, and intended scoring in the task metadata and review notes. Do not fabricate server IDs or copy another task's provenance.

## Preserve runs and trials

Use lowercase `run.json` under:

```text
rollouts/<model-harness>/<run-id>/
qc/<run-id>/
```

Keep `traces/` and `artifacts/` beside that record. A run can contain multiple result rows and traces. Match them by run ID, attempt, role, and trial name—not just filename or folder position.

Trace filenames may include a generated suffix. Follow the recorded trace reference rather than assuming every file is `attempt-1.json`. Keep native artifact subdirectories and the failure analysis with the attempt they describe.

## Check completeness before handoff

1. Freeze the exact task revision and record the source package hash.
2. Include the actual files and make required data or image dependencies accessible through the agreed delivery channel.
3. Record anything required that is still unavailable; an omission notice is not an artifact.
4. Verify that the environment builds, the reference check passes, and the negative control fails.
5. Preserve native work products, verifier output, and complete observable evidence.
6. Remove secrets, private reasoning, version-control internals, and unrelated temporary files from the delivery.
7. Record the delivered file inventory and hashes.

Do not convert graded workbooks, CAD files, or other native deliverables to PDF just to reduce size. See [Large evidence files](/guides/large-folder-uploads).

## Direct API submission

Source `TASK.json`, `run.json`, and traces are not the API's `TASK.json`, `RUN.json`, and `ROLLOUT.json` control documents.

Only a bundle built against the live API contract goes to `POST /api/v3/gdpx-submissions`. Follow [API bundle upload](/gdpx/evaluation-bundle-upload) for that separate layout, mapping, and validation. Do not rename source files to imitate it.
