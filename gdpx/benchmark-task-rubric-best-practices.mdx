GDPx measures whether a model can finish representative, economically useful knowledge work in a realistic environment. The unit is the whole job: kickoff, source material, tools, observable work, final artifact, deterministic checks, and rubric.

<Info>
  Roughly 0–50% pass@1 is a useful GDPx range. A zero-pass task can stay only if it is demonstrably solvable, the grader works, and model results still separate through partial credit.
</Info>

## Define the work

Start with the capability, not the file type. Name the practitioner, the decision or state change, and the errors that matter.

| Weak | Better |
| --- | --- |
| Produce a spreadsheet | Reconcile conflicting operating data and leave a decision-ready forecast with traceable assumptions |
| Summarize the documents | Triage an escalation across product, contract, and account history, then recommend the next action under policy |
| Use the tools correctly | Update a live operating artifact without breaking formulas or downstream dependencies |

Each task family should state who does the work, what outcome matters, and what a strong practitioner notices. Renaming companies or changing numbers does not create a new task family.

## Write both kickoffs

Ship two versions of the same job:

1. `kickoff.md`: the unstructured message a manager, client, or colleague would actually send.
2. `kickoff_structured.md`: the role, objective, constraints, and deliverable stated directly.

Both are required. The real-world version can rely on normal practitioner judgment, but every private policy, definition, and source fact must be discoverable in the environment.

Good ambiguity makes the model recover context. Bad ambiguity makes the task unsolvable.

## Build the environment

Use native files and realistic state. Do not replace a workbook, document, codebase, CAD file, or system record with a prose description of it.

For stateful or editable work, ship:

- the starting state and expected final state;
- intended changes and forbidden side effects;
- reset behavior between rollouts; and
- reopen, render, formula, executable, or diff checks that match the artifact.

The action space is a coding agent with provisioned CLI tools. List each tool and include its definition and skill documentation. Convert computer-use workflows into tool calls before submission.

## Grade observable work

Use deterministic checks for facts code can settle: values, schemas, formulas, compilation, geometry, state transitions, reconciliations, and artifact integrity. Use a judge for evidence-based recommendations, prioritization, material contradictions, and caveats that require practitioner judgment.

Each rubric criterion needs:

- a stable ID and one independently gradable claim;
- a weight and failure-mode tag;
- the observable evidence required to pass; and
- one aggregation rule for the task.

Report two scores: strict full-pass against the declared threshold, and a continuous capability score based on criteria met. Keep deterministic and judge results separate in the reward ledger.

Do not grade private reasoning or one preferred workflow. Alternate valid methods should pass.

## Calibrate the grader

Before cross-model runs, include a practitioner reference output, one to three known-bad outputs, and a partial-credit output when practical. State the expected per-criterion result for each anchor.

Change response length, order, and formatting without changing substance. The score should remain stable. Add plausible but irrelevant detail. The score should not improve.

False positives are more damaging than false negatives because they inflate measured capability. A benchmark item is not ready when the grader merely agrees with its author.

## Recommended: calibrate difficulty

For publishable difficulty claims, prefer at least three model tiers and enough independent rollouts to estimate pass@1 and criterion-level behavior. Regardless of the calibration envelope, pin the model, harness, prompts, tools, sampling settings, turn budget, timeout, judge version, context policy, and retry policy for every supplied rollout.

Review mean rubric score and per-criterion pass rates alongside pass@1. Treat a zero-pass item as unsolved at current capability, not as automatically difficult or broken. Before claiming that it is non-broken or suitable for the intended use, gather the following evidence when practical:

- a qualified practitioner can solve it with the exact context and tools;
- the practitioner output passes both grading layers;
- the environment is reliable;
- at least one model shows meaningful partial progress, or the task is explicitly beyond frontier; and
- the grader handles known-good, known-bad, and partial-credit anchors correctly.

If every model earns zero or near-zero partial credit, consider splitting or reworking the task. Items above roughly 50% pass@1 can serve as anchors, but they generally should not dominate the benchmark.

## GDPx standardized task bundle

The [Harbor task](/quickstart#the-runnable-task) is the portable runtime core. GDPx adds a canonical per-task layer so we can isolate the grader, reproduce a score, and normalize the task into the v15 bundle. This is the normalization target: you may author it directly or provide the batch evidence package below for reviewed adaptation.

```text
<TASK_ID>/
├── TASK.json
├── agent/
│   ├── kickoff.md
│   ├── kickoff_structured.md
│   ├── env/
│   └── tools/
├── grader/
│   ├── deterministic/
│   ├── rubric.json
│   └── validation.py        # or validation.ipynb
├── gold/
│   ├── reference_solution.*
│   └── adversarial/
└── samples/
    ├── rollouts/
    ├── RUN_MANIFEST.json
    └── reward_ledger.json
```

<Warning>
  Everything the model can access belongs under `agent/`. Nothing under `grader/` or `gold/` may be readable from the agent runtime. If grading needs a value, keep it in `grader/`, not in the environment the model explores.
</Warning>

### What each folder owns

| Path | Requirement | Contents |
| --- | --- | --- |
| `TASK.json` | Required | One machine-readable manifest for the task |
| `agent/` | Required | Both kickoffs, the native data room or environment, and docs for each provisioned tool |
| `grader/` | Required | Deterministic checks where applicable, the atomic rubric, and a script or notebook proving the signal exists in the data |
| `gold/` | Required | A strong-practitioner reference output and 1–3 known-bad responses that must fail |
| `samples/` | Required | A few full, untruncated rollouts, their run envelope, and the per-criterion reward ledger |

`RUN_MANIFEST.json` records the model and harness envelope plus token, tool, cost, and wall-clock data for each rollout. `reward_ledger.json` keeps deterministic output, judge output, and the final criterion contribution separate.

### `TASK.json`

Keep the manifest to the partner-supplied fields below. Standard Data adds revision IDs, hashes, bindings, and other canonical metadata during normalization.

| Group | Fields | Rules |
| --- | --- | --- |
| Identity | `task_id`, `partner`, `domain`, `family` | Folder name and `task_id` must match |
| Construct | `construct`, `turns`, `stateful`, `value_tier` | `turns` is `single` or `multi`; value tier is `high-judgment`, `mixed`, or `commodity` |
| Runtime | `action_space`, `tools`, `input_format`, `output_format` | `action_space` is `coding-agent`; every declared tool needs agent-visible docs |
| Scoring | `verifier_mix`, `scoring`, `difficulty` | Verifier weights sum to 1; record criterion count, full-pass threshold, calibration model, and target pass@1 |
| Horizon | `horizon`, `dual_paradigm_tested` | Record expected wall time and output tokens; test both modes when a direct-versus-tool choice exists |
| Evidence | `artifacts`, `provenance` | List agent, grader, and gold artifacts; state source, sanitization, rights, and overlap risk |

Numeric examples in templates are illustrative. Set criterion count, verifier mix, horizon, and threshold from the task. Use the GDPx difficulty band above.

### Five format rules

1. Ship both kickoff variants. A task with one is incomplete.
2. Use a coding agent with provisioned CLI tools. Do not submit a computer-use task.
3. Ship and grade native artifacts. Stateful work also needs pre-state, post-state, intended deltas, and forbidden side effects.
4. Keep the rubric atomic. Each criterion has one claim, a weight, a failure tag, and one declared aggregation rule.
5. Maintain one reward ledger. Record deterministic output, judge output, and final contribution per criterion.

## Package a delivery batch for upload

The single-task bundle above is the canonical normalized unit. A multi-task delivery uses an upstream batch envelope so the runnable task, complete rollout corpus, and QA documentation remain isolated from one another. Audit first stores the ZIP as a source bundle; an adapter preview must map its contents into canonical task units before import.

Do not copy the whole authoring bundle into the runtime directory. Export only the approved runnable task under `tasks/`. Keep trajectories under `trajectory/` and supporting material under `docs/`.

<Info>
  The batch handoff uses `trajectory/` in the singular. Every task name must match exactly across `tasks/`, `trajectory/`, and `docs/`.
</Info>

### Batch archive layout

Create one top-level directory named `<dataset>-<batch>-<num>/` and package that directory as a ZIP.

```text
<dataset>-<batch>-<num>/
├── tasks/                                      # required: runnable tasks only
│   └── <task_name>/
│       ├── task.toml
│       ├── instruction.md
│       ├── environment/                        # Dockerfile and workspace
│       ├── tests/
│       │   └── test.sh                         # writes /logs/verifier/reward.json
│       └── solution/
│           └── solve.sh                        # optional when the Oracle has another form
├── trajectory/                                 # required: full rollout evidence
│   └── <task_name>/
│       └── <model_name>/
│           └── rollout_<harness@version>_<n>/
│               ├── trajectory.json             # ATIF-format full trace
│               ├── reward.json
│               └── failure_analysis/
│                   └── failure_analysis.md      # required for every failed rollout
├── environment/                                # required only for private images
│   ├── README.md                                # image-to-task map
│   └── <image_name>/
│       ├── <loadable image or full build context>
│       └── manifest.md                          # name:tag, digest, and load/build steps
└── docs/                                        # required: never part of the agent runtime
    ├── failure_analysis_metadata.md             # required
    ├── README.md                                # recommended batch summary
    ├── reward_hacking.md                        # recommended reward-integrity review
    └── <task_name>/
        └── report.md                            # recommended task report
```

The archive may contain more evidence under `trajectory/` and `docs/`, but `tasks/` must stay harness-ready. Do not place reports, review notes, hidden grading values, or rollout analysis inside a runnable task.

Keep the authoring artifacts from the standardized task bundle:

| Authoring artifact | Batch destination |
| --- | --- |
| Approved unstructured kickoff | `tasks/<task_name>/instruction.md` |
| Structured kickoff, `TASK.json`, provenance, and rubric rationale | `docs/<task_name>/` or its documented subdirectories |
| Agent environment and tool definitions | `tasks/<task_name>/environment/` |
| Deterministic grader | `tasks/<task_name>/tests/` with verifier-only runtime visibility |
| Oracle or reference solution | `tasks/<task_name>/solution/` or an equivalent verifier-only reference |
| Rollouts, run envelope, rewards, and failure analyses | `trajectory/<task_name>/...` |
| Known-good and known-bad calibration artifacts | `docs/<task_name>/` as grader-only evidence |

Keep the complete rollout corpus in the batch archive. A normalized per-task `samples/` directory may contain a representative subset, but `RUN_MANIFEST.json` and `reward_ledger.json` must reconcile to the complete delivered evidence.

### Prepare the ZIP

1. Verify that every task has matching entries under `tasks/`, `trajectory/`, and `docs/`.
2. Remove `.git/`, `.DS_Store`, `__MACOSX/`, symbolic links, secrets, temporary files, and unrelated build output.
3. Confirm that each environment builds from the delivered files alone. Pin or include every base image, dependency, workspace asset, tool definition, and skill document.
4. Put exactly one batch root in the archive. Do not upload several unrelated roots or a directory-only ZIP.
5. Record the final filename, byte size, media type `application/zip`, and SHA-256 of the exact bytes you will upload.
6. Test the methodology document with the [audit endpoint](/gdpx/audit-endpoint). When intake capability reports `ready`, [submit the workspace ZIP](/gdpx/import-approved-tasks); the exact archive must pass v15 admission before automatic import.

<Warning>
  The document preflight endpoint accepts one PDF, DOCX, Markdown, or JSON document. It does not accept this ZIP. The canonical flow performs the resumable upload, quarantine, scanning, and adapter preview. A successful byte upload is not task acceptance: stop if the preview is blocked, incomplete, or does not map every task and visibility boundary exactly.
</Warning>

Raw preference pairs, pure trajectory collections, catalogs, and other data that cannot be represented as verifiable runnable tasks use a separate intake path. Do not force them into this archive shape.

### Make environments self-contained

Every task environment must build from the delivered files without access to an undisclosed registry or local workstation state. Pin dependencies and include the complete workspace and build context.

If a task uses a private image, add the root-level `environment/` package. Supply a loadable or reproducible artifact such as an exported image, OCI layout, or Dockerfile with its full build context. Its manifest must record the exact `name:tag`, digest, registry when applicable, and load or build instructions. The root `environment/README.md` maps each image to every dependent task.

Public images should be pinned by digest. Do not submit a task that depends on an image the reviewer or execution worker cannot retrieve or reconstruct.

## Recommended acceptance checks

Run these checks after the final image and task bytes are fixed. They are strong QA signals and should drive rework when applied, but they are not required task-taxonomy fields.

| Gate | Check | Pass condition | Failure meaning |
| --- | --- | --- | --- |
| G0 | Buildable environment | The environment builds from delivered files with no missing dependencies, base images, or workspace assets | Unbuildable or incomplete environment |
| G1 | Oracle = 1.0 | The reference solution produces reward exactly `1.0` when a reasonable Oracle can be supplied | Missing or broken Oracle |
| G2 | No-op = 0.0 | Doing nothing produces reward exactly `0.0` | Reward leakage or vacuous tests |

`tests/test.sh` must write the final reward to `/logs/verifier/reward.json`. Do not pre-generate this file in the task. The harness must keep tests, solutions, gold material, and hidden grading values unreadable to the agent.

The shell Oracle is optional when it is the wrong representation for the task. Prefer an equivalent known-good artifact and a reproducible way to show that it passes.

## Recommended difficulty evidence

Use full, untruncated trajectories. Pin the model, harness, harness version, prompts, tool definitions, sampling settings, turn budget, timeout, context policy, retry policy, and judge version.

For an early difficulty study, the following is a practical minimum envelope. Treat it as calibration guidance, not a universal acceptance gate. Prefer at least one additional model tier.

| Tier | Minimum evidence | Difficulty condition |
| --- | --- | --- |
| Baseline reasoning model | At least 16 independent rollouts | Resolve rate strictly below `50%`; at 16 runs, no more than 7 resolves |
| Frontier model | At least 5 independent rollouts | At most 2 resolves, or `40%` |

For published analysis, report `pass@1`, unbiased `pass@10` when `n >= 10`, `mean@10`, mean score, per-criterion pass rates, reward variance, token and cost distributions, wall-clock distributions, failures, timeouts, multiple seeds, and uncertainty. For RL, the productive core usually centers on `pass@1 = 0.5` with a `[0.25, 0.75]` training band and optional declared curriculum tails. For benchmarks, prefer a discrimination range where at least one frontier model scores above `0.30` and no model exceeds `0.85`. These are distributional diagnostics, not rigid per-task gates.

Use a reproducible baseline reasoning profile and a pinned frontier profile. Highlight tasks where the frontier profile resolves consistently while the baseline consistently fails.

If both tiers resolve a task zero times, do not infer difficulty from failure alone. Classify it as unsolved at current capability, then use a known-good artifact, qualified-practitioner check, or the optional calibrated-hint procedure below to investigate non-brokenness. Recompute every pass rate after excluding confirmed reward-hacked runs.

You may summarize a rollout set in `task.toml`:

```toml
[rollout_baseline.model]
name = "<full-model-name>"
harness = "<harness-name>"
rollout_n = 16
reward_mean = 0.25
reward_std = 0.43
reward_min = 0.0
reward_max = 1.0
pass_rate = 0.25
mean_steps = 54.0
mean_cost_usd = 0.42
mean_prompt_tokens = 12500
mean_completion_tokens = 4200
```

Treat these values as a summary of the delivered `reward.json` files, not as a substitute for them.

## Recommended: use hints as causal probes

A hint is an optional diagnostic, not a required taxonomy field. It has two purposes: investigate whether a zero-resolve task is solvable in principle and test whether a proposed failure mode caused the observed failure. Keep hinted and unhinted runs in separate, pinned evaluation conditions.

For each probe:

1. Select a failed trajectory and identify its likely root cause. A symptom such as “the patch is wrong” is not a root cause.
2. Write a hint that addresses the suspected cause without giving away the answer.
3. Add the hint to the instruction and rerun the same pinned evaluation envelope.
4. Record the exact hint, calibration rationale, rerun outcome, and interpretation.

A calibrated hint occupies the narrow band between two bad extremes:

- **Over-specified:** It names the exact file, function, constraint, or solution the agent was expected to discover.
- **Under-specified:** It asks the agent to “try harder,” “pay attention,” or otherwise gives no actionable direction.
- **Calibrated:** It names the dimension that needs attention—such as exploration completeness, regression safety, edge cases, or API contracts—while leaving the actual discovery to the agent.

Partial progress can validate a failure label when the hinted run gets past the original failure and later fails elsewhere. Demonstrating that a zero-resolve task is non-broken is stricter: a calibrated partial hint must enable an agent to solve the task without directly revealing the solution.

Interpret outcomes explicitly:

- The agent surpasses the failure after a calibrated hint: the proposed failure mode has causal support.
- The hint does not change behavior: the label remains unverified and may be wrong.
- Only an answer-revealing hint works: investigate a broken environment, false negative, false positive, or task-construction defect.

Unvalidated labels are hypotheses, not confirmed failure modes.

## Analyze every failed trajectory

Every delivered failed rollout needs `trajectory/<task_name>/<model_name>/rollout_<harness@version>_<n>/failure_analysis/failure_analysis.md`. The declared evaluation plan determines the rollout count; every failed attempt in the delivered corpus needs its own analysis.

Each file must include:

- the failure-mode label or labels from a versioned taxonomy;
- root-cause analysis grounded in observable evidence rather than a surface symptom;
- exact references to the relevant turn, tool call, state transition, artifact, rubric criterion, prompt segment, or grader output;
- the qualified-practitioner solvability result under the same context and tools;
- a status of confirmed, hypothesis, or ambiguous-needs-human-review, with confidence and review method; and
- when a calibrated hint or another causal probe was used, the exact probe, calibration rationale, rerun result, and interpretation.

Characterize each task as concentrated when failures cluster around one or two modes, or diverse when it exhibits 10 or more distinct reasons. For three through nine modes, report the exact count without forcing a label. No pattern is automatically better; explain the evaluation or training signal it provides.

The root `docs/failure_analysis_metadata.md` must contain methodology and distribution:

1. **Methodology:** the complete taxonomy and definitions, how reviewers inspect trajectories and assign causes, the solvability gate, validation and confidence rules, optional causal-probe handling, reviewer or judge calibration, and analysis quality checks.
2. **Per-model distribution:** counts and frequencies by model family, sample sizes, uncertainty caveats, and representative evidence-backed examples for material buckets.
3. **Cross-task distribution:** aggregate counts and frequencies for every mode, named task or tool clusters, dominant and rare patterns, and structural failure flags.
4. **Task histogram:** counts of tasks with one, two, three, and so on distinct failure modes.

## Recommended: document reward integrity

Reward hacking means receiving reward by gaming the verifier instead of solving the intended task. Examples include hardcoding expected outputs, editing or disabling tests, exploiting verifier paths, or exiting early after fabricating a reward file. Audit passing trajectories as well as failed ones; suspicious success is often the strongest signal.

When supplied, the root `docs/reward_hacking.md` should cover four areas:

1. **Observation:** identify affected tasks, models, and trajectories and describe the exploit. If none were found, say so and describe the breadth of the audit.
2. **Detection:** explain manual, automated, or judge-assisted review; include signals such as unusually short runs, test modification, out-of-band reward-file writes, and passes without work on the intended surface.
3. **Prevention:** document verifier hardening, intended-surface checks, and task revisions made to close loopholes.
4. **Suggestions:** record residual risks, structurally vulnerable task patterns, and downstream mitigations such as judge-based verification.

Retain every confirmed exploited run as evidence, exclude it from resolves, and recompute difficulty statistics. Record the adjustment.

## Recommended: write complete reports

A detailed `docs/<task_name>/report.md` is useful when a task needs more than its structured evidence. Cover the rollout envelope, failure analysis and distribution, reward-integrity observations, known limitations, and non-brokenness evidence when relevant.

At the dataset level:

- `docs/README.md` may summarize scope, task inventory, model and harness pins, and known limitations.
- `docs/failure_analysis_metadata.md` is required and contains the cross-task methodology and distributions.
- `docs/reward_hacking.md` is recommended and contains observations, detection, prevention, suggestions, exclusions, and residual risk.

Justify quality across each component and relationship:

| Surface | What to prove |
| --- | --- |
| Instruction ↔ environment | Information is placed deliberately; the instruction is minimal, while discoverable facts remain in the environment |
| Instruction ↔ verifier | The verifier checks exactly what the instruction requests; a mismatch is a severe defect |
| Tests and verifier | Coverage is comprehensive, resists reward hacking, and controls false positives and false negatives |
| Model-assisted judge | The judge is callable through the approved execution interface and its model, prompt, version, and evidence inputs are pinned |
| Solution or reference | It passes for the intended reason; report whether it also has instructional value |
| Configuration | Timeouts, resources, and settings are sensible; express memory as an integer number of MB |
| Documentation | Every claim is accurate, complete, attributable, and consistent with task, rollout, and reward evidence |

## Batch review checklist

Required:

- One ZIP contains one correctly named batch root.
- Task names match exactly across `tasks/`, `trajectory/`, and `docs/`.
- `tasks/` contains only runnable task material.
- Every environment is complete, pinned, resettable, and buildable from delivered files.
- Private images include a loadable artifact or full build context, exact tag and digest, instructions, and task mapping.
- Every verifier writes `/logs/verifier/reward.json` at runtime.
- Model, harness, version, prompt, tool, sampling, budget, timeout, context, judge, and retry settings are pinned for every supplied rollout.
- Every failed rollout has evidence-backed root-cause analysis, a taxonomy label, solvability status, and confidence or ambiguity status.
- Dataset-level failure taxonomy, per-model and cross-task distributions, and the task-count histogram are complete.
- Agent-visible, verifier-only, solution, and gold boundaries are enforced by the runtime, not merely described in prose.
- Minimal source, rights, sanitization, and overlap-risk metadata is present.

Recommended:

- G0, G1, and G2 pass on the final delivered bytes.
- Baseline and frontier rollout counts and pass rates support the declared difficulty positioning.
- Zero-resolve tasks include calibrated non-brokenness evidence.
- Calibrated hints or other causal probes support important failure hypotheses.
- Passing trajectories were audited for reward hacking, and confirmed exploited runs were excluded from pass rates.
- Per-task reports and batch summaries explain limitations and material findings.

## Partner delivery and Standard Data review

The complete handoff includes either the canonical task bundle above or a batch evidence archive that can be mapped into it without inventing missing facts. Partners supply the source assets, minimal source and rights metadata, sanitization notes, rubric rationale, tool definitions, and known-good or known-bad artifacts that Standard Data cannot create on their behalf.

Standard Data runs the integrity pass:

- verifier stress tests and false-positive or false-negative analysis;
- cross-model discrimination and difficulty measurement;
- pass-condition tightness, judge bias, and reward-hacking probes;
- contamination and leakage checks; and
- manual trajectory review and judge calibration against experts.

If experts review rollouts during development, keep a simple log in `samples/`. Record the reviewer, task revision, decision, and rationale. Do not discard it; later agreement analysis depends on the original review data.

## Partner checklist

- A qualified practitioner can solve the task using only the supplied context and tools.
- Both kickoffs ask for the same job.
- Native inputs open, and the environment resets cleanly.
- The reference output passes; known-bad outputs fail for the intended reason.
- Deterministic checks cover everything code can settle.
- Every judge criterion is atomic and cites observable evidence.
- Alternate valid methods are not penalized.
- Agent-visible, grader-only, and gold files are isolated correctly.
- Source, rights, sanitization, and overlap-risk metadata are complete.

Use the [audit endpoint](/gdpx/audit-endpoint) for non-canonical document feedback while authoring. A clean document audit is not a v15 workspace result, and its legacy `ready_to_submit` field never authorizes a ZIP. When the capability endpoint reports `ready`, [submit the workspace](/gdpx/import-approved-tasks); the exact archive must pass the pinned v15 preflight before automatic import.
