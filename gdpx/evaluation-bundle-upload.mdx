`POST /api/v3/gdpx-submissions` is the only submission path that can publish a task into the GDPx/Wilderness catalog. It accepts a ZIP that binds runnable task bytes, rollout evidence, criterion decisions, and review artifacts into one immutable delivery.

Start with [GDPx workflow](/gdpx/workflow) for the end-to-end sequence and the
boundary between partner, operator, and Wilderness responsibilities.

<Warning>
  A successful byte upload is not publication. A task appears in Wilderness only
  after managed execution approval, current-policy `review_ready` status, and
  inclusion in the active catalog revision. A task with missing or
  irreconcilable evidence remains in Audit as `blocked` and is not included in
  the active GDPx catalog.
</Warning>

The legacy `/api/v2/workspace-submissions` workflow may still create draft Audit revisions. It cannot add a task to the GDPx benchmark revision or Wilderness catalog.

## Authenticate and discover the contract

Use the shared Standard Data API origin and a tenant-scoped key:

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"
```

Read capabilities and the current JSON Schema before building a bundle:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/capabilities" \
  --output gdpx-capabilities.json

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/schemas/review-bundle" \
  --output gdpx-review-bundle.schema.json

OPENAPI_PATH="$(jq -r '.openapi_endpoint // ""' gdpx-capabilities.json)"
if [ -n "${OPENAPI_PATH}" ]; then
  curl --fail-with-body \
    --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
    "${STANDARD_DATA_API_BASE}${OPENAPI_PATH}" \
    --output gdpx-openapi.json
fi
```

Creating a submission requires `uploads:write` and `imports:write`. Polling `GET /api/v3/gdpx-submissions/{gdpx_submission_id}` requires `imports:write`, including when you follow the returned `self` link. Capabilities, schema, catalog, readiness, and rollout reads require `tasks:read`. Authentication is always tenant-bound.

Call the authenticated OpenAPI 3.1 route only when capabilities include `openapi_endpoint`. It requires `tasks:read`, rejects anonymous and upload-only credentials, and returns a private, non-cacheable response. Absence of that field means the route is not deployed on that API release. This page documents the v1.1 submission schema, `https://standard-data.dev/contracts/gdpx-review-bundle/1.1.0/schema.json`. Use it only when the capability response advertises v1.1.

The capability response is authoritative for the active contract version, maximum ZIP size, supported adapter modes, publication policy, and resumable-upload limits. Do not hard-code those values from an older response.

<Warning>
  Submission is fail-closed. Offer an upload action only when `/v1/whoami`
  reports `canonical_submission.state` as `ready` **and**
  `/api/v3/gdpx/capabilities` reports `access.can_submit` as `true`. Inspect
  `admission.blockers` when it is false. During a controlled rollout, admission
  may be disabled or tenant-allowlisted even though the schema and read APIs are
  reachable.
</Warning>

## Canonical ZIP layout

Under `gdpx-review-bundle/1.1.0`, a `task_and_evidence` ZIP contains 1–100 unique tasks. Each task has exactly one evaluation and one QC1 rollout, and the entire set imports atomically:

```text
GDPX_BUNDLE.json
INTERNAL_QA_CREDENTIAL_ATTESTATION.json   # internal-QA deliveries only
tasks/
└── <task_id>/
    ├── TASK.json
    ├── PUBLICATION_AUTHORITY.json
    ├── task.toml
    ├── instruction.md
    ├── environment/
    ├── tests/
    └── solution/
evaluations/
└── <task_id>/
    └── <run_id>/
        ├── RUN.json
        └── <rollout_id>/
            ├── ROLLOUT.json
            ├── trajectory.atif.json
            ├── verifier.json
            ├── criterion-decisions.json
            └── artifacts/
```

`GDPX_BUNDLE.json` is a complete inventory of every other retained file in the ZIP. Do not add `GDPX_BUNDLE.json` to its own inventory. For each archive file except the manifest itself—including any other root-level control file—record its normalized relative path, byte size, media type, and SHA-256. The manifest binds every task, run, and rollout to the exact `task_id`, `task_revision_id`, `logical_task_id`, `run_id`, and `rollout_id`. Task, revision, logical-task, run, and rollout identities must be unique across the ZIP. Multiple rollouts for one task remain invalid; create another immutable submission for another attempt. `evidence_only` remains a one-task append to its declared `target_task_revision_id`.

`TASK.json` uses `gdpx-task/1.1.0`. It binds the exact prompt, rubric, verifier, `task_content_sha256`, and a complete `workspace_files` inventory. Each workspace entry declares its normalized path, SHA-256, byte size, media type, artifact kind, and visibility. `environment.workspace_inventory_sha256` covers the sorted inventory, including every one of those fields. `RUN.json` uses `gdpx-run/1.1.0` and must repeat the same workspace-inventory binding. The canonical submission baseline remains `gdpx-rollout/1.1.0`; its ordinary derived Master baseline is `gdpx-master-evidence/1.1.0`.

A successful managed native normalization produces a separate typed `gdpx-rollout/1.2.1` and materializes `gdpx-master-evidence/1.2.1`. These are derived managed evidence records, not a new public review-bundle version and not values to substitute into a `gdpx-review-bundle/1.1.0` upload. Existing typed `gdpx-rollout/1.2.0` and `gdpx-master-evidence/1.2.0` records remain readable as immutable compatibility evidence. They cannot be emitted by a new managed capture or become newly publishable because they do not bind native criterion-chunk provenance.

For a current rollout with `provenance.source_type: "regraded"`, `provenance.source_sha256` is required and must bind the exact retained pre-regrade Master. A current non-regraded rollout must omit that field. Retained `gdpx-rollout/1.0.0` sources remain readable under their frozen schema, which did not define `provenance.source_sha256`. A legacy 1.0 rollout marked `regraded` therefore remains a read-only draft and cannot materialize current Master evidence or a publication candidate. Do not add a 1.1 field to historical bytes; create new 1.1 regraded evidence through the signed-intent and processor-finalization path below.

<Warning>
  Do not treat an environment directory hash, image digest, file count, or list
  of paths as a workspace inventory. Every agent-visible, tool-mediated,
  verifier-only, and publication-only task file must appear with its exact path,
  hash, size, media type, kind, and visibility.
</Warning>

### Strict JSON and canonical hashing

Every JSON document whose exact retained bytes become evidence, authority, scan or transformation input, or a signed/hash-bound managed-runtime record uses strict UTF-8 before schema validation, projection, hashing, or signing. At those exact-evidence boundaries, Audit rejects duplicate object keys, integral numbers outside JavaScript's safe integer range, unpaired Unicode surrogates, non-finite numbers, trailing content, and values outside the JSON data model. Valid values are hashed as RFC 8785/JCS canonical JSON; source-object SHA-256 fields still bind the exact retained bytes. Ordinary API request envelopes continue to use their documented request-schema validation and are not evidence merely because they are authenticated.

Do not rely on a parser's last-key-wins behavior, float coercion, Unicode replacement, or property order. A document that would decode differently across implementations is invalid rather than normalized into evidence.

### Uploaded publication declaration

Every task submitted with `publication_policy: "publish_when_review_ready"` must include `tasks/<task_id>/PUBLICATION_AUTHORITY.json` using `gdpx-publication-authority/1.1.0`. The bundle manifest records that file with role `publication_authority` and binds its path and SHA-256 from the task descriptor. Missing, blocked, mismatched, or tampered declaration evidence is a publication blocker even when every technical evaluation check passes.

The partner-uploaded declaration binds the exact task, task-content hash, workspace-inventory hash, logical task, source delivery, rights basis, agreement status, owner intent, and source mappings. Its self-attestation hash covers the canonical JSON record. An external-catalog declaration must state `publication_target: "external_catalog"`, set `intended_catalog_member: true`, carry an applicable executed-agreement or first-party rights basis, and include approval scoped to `gdpx_benchmark_qc_and_publication`.

The uploaded declaration is necessary but not sufficient. Audit separately requires an immutable publication-rights grant in Standard Data's operator-controlled registry and an active authority head that resolves to that grant. The grant and head bind the exact declaration, source delivery, task-content hash, and workspace-inventory hash. Submission credentials cannot create, replace, or advance either record.

If the active policy changes or an owner revokes publication, Audit first publishes a replacement catalog revision that excludes the task, then advances the authority head to the new immutable decision. The old grant, head revision, benchmark membership, task, and evidence remain in history. The current readiness projection becomes blocked. Audit never silently rewrites the old benchmark membership or makes the active catalog unavailable during revocation.

<Warning>
  Upload permission is not publication authority. A valid API key, successful
  transport, complete rollout, partner declaration, self-hash, or technical
  candidate cannot substitute for a task-bound declaration, matching immutable
  operator grant, and current authority head. Never reuse an authority file
  across revisions or deliveries.
</Warning>

### Internal-QA exact-byte fixture retention

Use the internal-QA path only when an isolated benchmark world intentionally contains credential-like fixture literals that reviewers must inspect byte for byte. It is not a general secret-scanner exception.

An internal-QA bundle that includes `INTERNAL_QA_CREDENTIAL_ATTESTATION.json` is singleton-only: it must contain exactly one task, one run, and one rollout. Do not combine an attested internal-QA task with any other task or evaluation in the same ZIP.

The declaration must state `publication_target: "internal_qa"`, set `intended_catalog_member: false`, use a first-party rights basis, and include approval scoped to `gdpx_internal_qa_synthetic_fixture_retention`. Standard Data separately retains an operator-controlled `INTERNAL_QA_CREDENTIAL_STATEMENT.json` using `gdpx-internal-qa-credential-statement/1.0.0`. Its semantic statement hash, exact file hash, immutable control object, active grant, and authority-head generation are distinct bindings; an uploader cannot create or advance them.

The review bundle includes `INTERNAL_QA_CREDENTIAL_ATTESTATION.json` and inventories it in `GDPX_BUNDLE.json` with role `internal_qa_credential_attestation`. The attestation must include:

- a complete, sorted, hash-bound corpus covering every retained and projected credential-like occurrence;
- exactly one source-bound classification for every detector match;
- `synthetic_fixture_literal` records with exact source, fixture, and Master pointers and hashes, offline-world provenance, isolated execution, disabled network egress, and no environment, secret-manager, or provider origin;
- `non_value_syntax` records with parser proof for identifiers, expressions, and empty literals; and
- clean high-confidence, provider-format, and grouped-token entropy scans plus a `network_origin` verdict of `offline_only` over the same corpus hash.

Source and Master bytes must match the attested fixture bytes exactly. Placeholders, rewritten values, an incomplete corpus, an uncited match, or a blanket `internal` or `sanitized` flag blocks admission. Any byte, corpus, authority, or grant change requires a new statement, attestation, operator grant, and exact replay.

Internal-QA evidence may run through managed execution and remains readable to every authenticated tenant user with `tasks:read` while its exact active grant is valid. It never satisfies external-catalog readiness or membership. Revoking or replacing the grant closes every internal-QA review path without deleting immutable audit history.

An internal-QA admission writes only the immutable V3 review binding, admission terminal, exact access reservation, Master evidence, criterion chunks, and artifact bindings. It must not create a V2 task projection, workspace, supplied run, readiness attestation, family, data sheet, or catalog record. Legacy V2 records found for a review-only revision are stale migration artifacts and must remain excluded from every reader until an operator reviews the dry-run inventory.

### Managed execution and approval

An uploaded `RUN.json`, provider result, Harbor identifier, runtime receipt, or field that claims execution validation is evidence supplied by the uploader. It cannot authenticate its own execution.

There is no public managed-rollout launch endpoint. Submission credentials
cannot start a managed run or issue its approval. Give the Standard Data
operator the submission ID, exact task/run/rollout identities, task-content
hash, workspace-inventory hash, and required model/harness envelope. The
operator owns the managed launch and independent approval.

A rollout qualifies for QC1 publication only after Standard Data runs or verifies it through the approved managed execution path. The retained runtime receipt binds the exact task and workspace, run and rollout manifests, trajectory, verifier output, criterion ledger, work products, forensic sections, runtime configuration, harness result, logs, and immutable artifact hashes. After the evidence generations, Master, criterion chunks, and artifacts commit, Audit verifies their exact hashes and creates a separate operator-authenticated managed-execution approval for those canonical bytes.

The canonical and materialized workspace hashes are different authorities:

| Binding | Exact contents |
| --- | --- |
| `workspace_inventory_sha256` | Canonical descriptors under `tasks/<task_id>/source/...`, including path, size, SHA-256, media type, artifact kind, and visibility |
| `materialized_workspace_inventory_sha256` | Native files in the Harbor task root before canonical projection, including each native path, size, and SHA-256 |
| `workspace_file_mappings_sha256` | The complete one-to-one bridge between those two inventories |

For every native file, the mapping must use the exact native relative path and the exact canonical path `tasks/<task_id>/source/<native-path>`. Both sides repeat the same byte size and SHA-256. The canonical side also records media type, artifact kind, and visibility. Native paths and canonical paths are each unique, the mappings are ordered by canonical path, and the mapping digest binds the domain `standard-data/gdpx-workspace-file-mappings/v1` plus the complete mapping array. Missing, extra, rewritten, or byte-mismatched files fail closed. Never place the materialized hash in the canonical field or derive one hash from the other.

Managed capture retains the exact bytes for `result.json`, `config.json`, `lock.json`, `provider-readback.json`, `runtime-attestation.json`, `execution-binding.json`, `agent/trajectory.json`, `verifier/reward.json`, `verifier/criterion-report.json`, and every configured `artifacts/<output-path>`. The worker produces retained native result and observable-log objects, a task-materialization receipt, a worker receipt, sanitized logs, and work products. Receipts and approvals bind each object's path, role, byte size, SHA-256, and storage generation. A summary, provider ID, or reconstructed log cannot replace those bytes.

Managed `1.2.1` evidence also preserves the verifier's native chunk inventory. Each entry binds the exact unnormalized `native_chunk_id`, contiguous `sequence`, and SHA-256 of the complete native chunk. A second hash-bound inventory maps it one-to-one to the distinct canonical `criterionchunk_...` ID, canonical ordinal, and semantic content SHA-256. The semantic digest excludes storage generations from evidence references, because materialization can change a generation without changing canonical evidence bytes. Dropping a native chunk, reusing an identity, changing its order, or substituting a canonical ID for a native ID invalidates the rollout.

<Warning>
  The checked-in native capture, control-port, and canonicalization protocols do
  not establish deployment availability. The provider-native control service
  and independent canonicalizer remain external dependencies. Managed execution
  stays fail-closed until their exact deployments, service accounts, audiences,
  release hashes, IAM bindings, and provider observation adapters are pinned and
  advertised by capabilities. This documentation does not claim that a workload
  can currently be launched.
</Warning>

The approval is not part of the uploaded authority declaration and cannot be created by submission credentials. Until the exact approval exists and verifies, the run remains `not_execution_validated`. Audit keeps the first import as archive evidence, but it cannot satisfy QC1, become `review_ready`, enter Wilderness Results, or support catalog membership. After approval, replay or resubmit the exact hash-bound bundle when the capability response instructs you to do so; any byte change requires new verification and approval.

Trusted-runtime success requires the controller to finish the one-shot privilege attestation, independently validate the canonical create-only sidecar, bind that sidecar byte for byte to frame A, and only then open the model launch gate. Empty captured stdout and stderr do not establish success. An entirely empty stderr stream may omit the marker only when the sidecar and frame A both validate. If stderr contains any bytes, the marker must be unique, first, well formed, and byte-identical to the verified sidecar and frame A.

If trusted-runtime attestation is rejected before model launch, retain only bounded structural diagnostics: `missing_marker`, `duplicate_marker`, `marker_not_first`, `malformed_marker`, `missing_sidecar`, `malformed_sidecar`, `mismatched_sidecar_a`, `controller_timeout`, or `controller_terminated`; marker count and first-line status; capped stdout and stderr line and byte counts with truncation flags; whether a chunk was observed; return code when available; elapsed time; and sidecar presence and validity. `missing_marker` applies only when a non-empty stderr stream requires a marker. Never retain raw stdout, stderr, marker values, or sidecar bytes in this diagnostic. A pre-launch rejection produces no subject rollout, no score, and no QC1 credit. Display it as an execution rejection, never as score `0`. These are admission semantics, not a claim that a particular runtime build has passed a live canary.

Large trajectories and work products stay as hash-bound objects. Do not copy them into a metadata field or replace them with a summary.

### Required rollout evidence

Each rollout must retain:

- the exact prompt and relevant agent-visible context;
- an ordered observable trajectory with model messages, tool calls, tool results, environment events, and errors;
- the final model answer or primary work product;
- verifier output and all test results;
- exactly one decision for every declared rubric criterion, including blocked, not-applicable, and unscored criteria;
- score reconciliation, including aggregation, threshold, dependencies, and hard gates;
- model, harness, environment, verifier, and judge versions;
- duration, turns or steps, token usage, cost, stop condition, and execution outcome when supplied by the harness; and
- immutable artifact hashes and object generations.

The six forensic sections—Problem, Setup Logs, Agent Logs, Results, Test Logs, and Grading—must be present. A section with no applicable source data must use an explicit `not_applicable` status and a reason. Omitting a section is not equivalent to `not_applicable`.

### Criterion decisions

Each item in `criterion-decisions.json` must contain:

| Field                                           | Requirement                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------- |
| `criterion_id`                                  | Stable ID that exactly matches one source-rubric criterion                |
| `source_text`                                   | Exact source wording; do not paraphrase the grading contract              |
| `status`                                        | `passed`, `failed`, `partial`, `blocked`, `not_applicable`, or `unscored` |
| `weight`                                        | Source weight or scoring contribution when one exists                     |
| `awarded_contribution` / `maximum_contribution` | Awarded and possible contribution when applicable                         |
| `direct_result`                                 | Result before dependency or hard-gate effects                             |
| `cascaded_result`                               | Result after dependency or hard-gate effects                              |
| `dependency_criterion_ids`                      | Exact IDs of criteria that can cascade into this result                   |
| `grader`                                        | Verifier or judge identity and pinned version                             |
| `rationale`                                     | Human-readable explanation grounded in observable evidence                |
| `evidence_refs`                                 | Typed references to retained events, tests, outputs, or artifacts; at least one is required for `passed`, `failed`, or `partial` |

The criterion ledger must contain exactly one decision for every criterion declared by the source rubric. This includes criteria marked `blocked`, `not_applicable`, or `unscored`; do not omit them. The score-reconciliation object records the aggregation rule, reported score, calculated score, pass threshold, hard-gate results, and whether the values reconcile. A duplicate criterion ID, missing or unknown criterion, dangling evidence reference, or unexplained score mismatch blocks publication.

## Create a submission

Hash the exact ZIP and send one idempotent request:

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/api/v3/gdpx-submissions" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: gdpx-<stable-client-operation-id>" \
  --data '{
    "filename": "delivery.zip",
    "content_type": "application/zip",
    "size_bytes": 123456,
    "sha256": "<64-lowercase-hex>",
    "contract_version": "gdpx-review-bundle/1.1.0",
    "mode": "task_and_evidence",
    "target_task_revision_id": null,
    "adapter_mode": "canonical",
    "publication_policy": "publish_when_review_ready"
  }' \
  --output gdpx-submission.json
```

Request fields:

| Field                     | Accepted value                                 |
| ------------------------- | ---------------------------------------------- |
| `content_type`            | `application/zip`                              |
| `contract_version`        | `gdpx-review-bundle/1.1.0`                     |
| `mode`                    | `task_and_evidence` or `evidence_only`         |
| `target_task_revision_id` | Required for `evidence_only`; otherwise `null` |
| `adapter_mode`            | `canonical` or `terra_compatibility`           |
| `publication_policy`      | `publish_when_review_ready`                    |

Migration staging is not a public submission policy. A governed operator may retain complete candidate evidence through a separate authenticated workflow. A partner upload cannot select staging, advance a readiness head, or alter the active catalog's eligibility generation.

The response returns `gdpx_submission_id` plus same-origin relations for upload authorization, completion, polling, and cancellation. Upload signing and finalization reuse the v2 upload-session transport linked by the response. Follow those links. Do not construct storage URLs, persist resumable-session credentials, or send the Standard Data API key to object storage.

### Evidence-only submissions

Use `mode: "evidence_only"` only to attach one run and one rollout to a task revision that Audit already retains. Set `target_task_revision_id` to that exact revision. The submitted `TASK.json`, task-content hash, full workspace inventory, rubric, verifier, and environment bindings must exactly match the retained canonical task.

An evidence-only submission never changes the task head, replaces task bytes, creates a new task revision, or directly mutates the active catalog. Any mismatch blocks the submission. If the task changed, submit a new `task_and_evidence` bundle for the new immutable revision.

For an externally supplied evidence-only bundle, Audit first retains and verifies the exact source ZIP generation, signed compatibility authorization, signed completion, Master, criterion ledger, execution approval, and current task authority. It then freezes an immutable append candidate and stops before readiness, membership, catalog, or compatibility activation. An operator must explicitly admit that exact candidate hash against the expected catalog revision and generation. Admission creates a new immutable benchmark revision, preserves every existing rollout and the single qualifying QC1 anchor, appends the new rollout as non-qualifying evidence, prepares a hash-bound compatibility projection, and makes that projection eligible for selection only when the single compare-and-swap advances the matching v3 catalog head. A preparation or catalog conflict leaves the old cohort fully current. There is no public force or bypass parameter.

## Follow the workflow

```text
awaiting_upload → sanitizing → normalizing → validating → importing → review_ready
                                                                  └→ blocked
```

Poll `GET /api/v3/gdpx-submissions/{gdpx_submission_id}` or the returned `self` link with an `imports:write` credential. `blocked` is terminal for that immutable submission. Cancellation also ends in `blocked` with reason code `SUBMISSION_CANCELLED`; it does not introduce a separate workflow state. The result includes stable issue codes and JSON pointers to missing, mismatched, or unsafe fields.

Handle `blocked` according to its issue code:

- `GDPX_EVIDENCE_ONLY_OPERATOR_ADMISSION_REQUIRED` means Audit already verified the external evidence-only delivery and froze an exact append candidate. Do not edit or resubmit it. Give the retained candidate ID, candidate SHA-256, and expected catalog revision and generation to the operator admission workflow. The operator either admits those exact bytes or rejects the stale candidate; the public submission remains terminal.
- A malformed, incomplete, mismatched, or otherwise unfrozen source package has no admissible append candidate. Correct the reported source fields and create a new submission. Do not reuse the old submission ID or claim that its terminal record changed.

Validation is all-or-nothing for publication. It verifies identity bindings, task and workspace hashes, publication declaration, active rights grant and head, managed-execution approval, artifact availability, rubric completeness, criterion evidence, score reconciliation, runtime status, secret scanning, and omission of private reasoning.

The complete publication sequence is:

```text
v3 submission and archive-only import
  → managed QC1 run and retained runtime receipt
  → server verification of committed evidence generations
  → immutable operator-authenticated managed-execution approval
  → exact bundle replay or resubmission when advertised
  → current-policy review-readiness attestation
  → immutable benchmark-revision membership
  → active GDPx catalog head
```

### Catalog admission and reader activation

`review_ready` is an immutable attestation for one exact task revision, qualifying rollout, Master projection, and policy version. It does not make a task visible by itself. Audit copies that attestation ID and SHA-256 into an immutable benchmark-revision membership, then advances the active GDPx catalog head to the complete benchmark revision. The membership-bound attestation—not a mutable latest-readiness pointer—is the catalog authority.

A catalog task may retain several complete QC1 rollouts, but exactly one admission is the qualifying QC1 anchor bound by membership and readiness. Every rollout exposed as current, publishable evidence must independently satisfy the current readiness policy, including complete evidence, execution approval, compatibility completion, task and workspace identity, source-archive retention, and artifact checks. Historical or compatibility-readable evidence may remain retained without being current or publishable. Additional current rollouts never replace or silently promote themselves over the anchor.

Any compatibility projection used by older readers is prepared and hash-verified before publication, but remains hidden. Audit activates it only after the active v3 catalog admits the same task revision, run, rollout, Master hash, and evidence hash. A partial write therefore cannot expose a score without its Master evidence. Retrying an interrupted activation reuses the retained immutable authorization and completion bindings; it does not mint a different rollout or mutate the historical membership.

The GDPx tab reads `GET /api/v3/gdpx/catalog/current`. It does not infer membership from publication flags, creator labels, run counts, legacy stage labels, or a mutable `is_current` field.

The catalog returns lightweight admitted-rollout identities and evidence hashes. Retrieve the catalog-selected readiness attestation, including its execution approval and compatibility binding, from the review-readiness endpoint. Retrieve Master evidence, criterion chunks, transformation history, and artifact links from the task rollout endpoint.

`review_ready` always means ready under the policy recorded by that attestation. A historical readiness attestation remains immutable. A changed rights head, revoked authorization, mismatched execution approval, or newer policy requires new matching records and a new benchmark revision before the catalog can change; staging or changing a draft/latest readiness pointer alone never changes what Wilderness serves.

Before publication, inspect the submission resource and its `blocking_issues`; the catalog-selected review-readiness route returns `404` for an unpublished or internal-QA-only revision. After publication, verify the exact task revision:

```text
GET /api/v3/tasks/{task_revision_id}/review-readiness
GET /api/v3/tasks/{task_revision_id}/runs/{run_id}/rollouts/{rollout_id}
GET /api/v3/gdpx/catalog/current
```

The active catalog is the immutable benchmark revision selected by that durable catalog head.

<Warning>
  GDPx publication is not a temporary preview. Submit only task revisions
  intended to remain in the tenant's benchmark history. Corrections create a new
  immutable revision for the same logical task. The public v3 API does not
  delete evidence or change publication authority; an operator-controlled
  revocation excludes a task through a new head and catalog revision without
  erasing history.
</Warning>

## Terra compatibility mode

Choose `terra_compatibility` only for a legacy or partner-specific package that cannot be emitted canonically **and** only when the current capabilities response lists `terra_compatibility` in `adapter_modes`. If the server does not advertise that adapter, submit a canonical bundle or wait for the trusted adapter to become available; never emulate the adapter client-side. The capabilities response and fetched schema—not this page or a cached client copy—are authoritative for availability and accepted fields.

When advertised, the pinned compatibility model may identify source files, map heterogeneous fields, and assign source-derived stable IDs. It does not summarize or paraphrase source evidence. Any presentation field it emits must reproduce a source-bound value under the exact locator rules below. Its exact model revision, adapter prompt version, and release are recorded in the normalized evidence. The public contract does not permit callers to select or substitute a model.

Terra must not:

- rewrite task instructions or rubric meaning;
- change weights, thresholds, dependencies, or hard gates;
- invent a prompt, output, test, grading decision, or evidence;
- summarize or paraphrase retained source evidence;
- infer missing facts from domain knowledge; or
- authoritatively rescore the rollout.

Every generated field records its exact source path and file SHA-256, RFC 6901 pointer or retained byte span, input and output hashes, model revision, adapter prompt version, and timestamp. Stable derived IDs bind those source locators; identical values in different locations must not alias. An ambiguous, uncited, colliding, or source-unbound mapping blocks publication. Legacy adapter records remain readable under their frozen contract but cannot create a new transformation.

Source transport bytes remain inside the recovery-source boundary. Audit copies normalized bundles, transformation records, and certification provenance create-only into the canonical certification store. Before admission, it verifies the exact bucket, object, generation, size, media type, and SHA-256.

If an exact rubric and final output exist but the criterion ledger is absent, rerun the original verifier or judge against the retained output. A policy-approved stronger compatible judge may be used under the judge-dominance rule, but the result must be labeled as regrading. Preserve both scores and block publication for adjudication if they disagree.

Regrading uses a two-stage integrity boundary. Before import, a KMS-signed, one-time intent binds the exact original evidence, unchanged subject attempt, replay inputs, grader, and policy approval. Audit retains and verifies the original bundle before it accepts the regenerated bundle.

After import, Audit—not the model or uploader—derives the regenerated Master, evidence-commit, criterion-ledger, complete subject-evidence, and final-output-manifest hashes. It then writes the immutable dual-ledger record. The intent progresses from `reserved` to `produced` to `completed`; Audit consumes it only after the dual ledger is durable. A pre-import service cannot declare final hashes. A crash between phases must resume the same immutable intent instead of minting another attempt.

The regrader protocol is a deterministic `ensure`/`readback` exchange. Both operations bind the complete authorized request, provider operation and result hashes, and the exact grader release. A timeout, disconnect, or process crash is ambiguous—not a terminal failure—so recovery reads the existing provider result and resumes the same reservation instead of launching another grading call.

Recovery history is append-only and compare-and-swap protected. An expired intent that was never reserved may receive a successor only after the authority atomically records an authenticated `absent_fenced` retirement; that fence and any late reservation contend in the same transaction. Reserved, produced, completed, failed, and otherwise ambiguous intents are never renewed. Concurrent recovery attempts must converge on the winning journal generation, and any missing narrow journal store blocks regrading rather than risking a duplicate judge call.

Judge dominance is an explicit approval, not a model-name comparison made by the uploader. The approval binds the tenant, exact task revision, rubric SHA-256, declared judge identity and digest, replacement judge identity and digest, compatibility finding, dominance finding, policy hash, approver, rationale, and timestamp. The replacement must be a different judge, must evaluate the unchanged retained output under the same scoring contract, and must be approved as both compatible with and stronger than the declared judge. An exact replay with the original judge does not require dominance approval. A missing approval, a changed rubric or output, or a score disagreement blocks publication pending adjudication.

## Legacy migration and reruns

For existing tasks, recover evidence in this order:

1. canonical retained Audit evidence;
2. reviewer-evidence companions;
3. immutable release artifacts; and
4. the original partner delivery.

A derived Master projection must cite those retained sources and record the transformer version. It may improve presentation, but it may not invent missing primary evidence.

Regrade a retained final output when the source rubric and verifier are available. Run a fresh GPT-5.6 Luna QC1 rollout only when primary evidence cannot be recovered or the task revision changed. Bind a rerun to the exact immutable revision and native harness; do not use a new run to overwrite historical evidence.

### Operator migration boundary

There is no public batch-migration endpoint. A migration inventory or report does not import evidence, approve execution, establish current readiness, or publish a catalog. Operators recover each exact task/run/rollout from canonical Audit evidence, reviewer companions, immutable release artifacts, and the original partner delivery—in that order. Complete candidates then enter a separate, disabled-by-default internal staging service; partners cannot select this mode through `/api/v3/gdpx-submissions`.

The staging service accepts only the dedicated Google OIDC service account and an exact source object locator: bucket, object, generation, byte size, media type, and SHA-256. It copies the ZIP create-only into the private canonical upload boundary. It binds the copy to a deterministic submission and staging intent, completes the normal scanner and processor path, and waits for a durable `retained_inactive` receipt.

The receipt binds the reviewed migration report and plan, task revision, stage role, requested and retained object locators, canonical task and workspace hashes, compatibility completion, and immutable readiness-attestation ID and digest. Staging retains complete evidence. It never advances a readiness head, eligibility epoch, compatibility reader, benchmark membership, or catalog head.

Every phase is idempotent. A retry after source copy, intent retention, upload finalization, queue dispatch, or processor completion must resume and verify the same objects and records. It must not create a different submission, replace bytes, or treat a missing receipt as success.

Local recovery sources may enter the operator boundary only through the create-only source-promotion command. It writes content-addressed objects and accepts an existing object only after tenant metadata, exact generation, size, media type, SHA-256, and byte readback reconcile. Promotion produces a distinct immutable cloud-bound source manifest. It does not authorize a model call, QC1 launch, submission, membership change, or catalog switch.

Source promotion must run as the dedicated migration source-promoter identity with create/readback-only access to the exact source prefix. Developer ADC, the public API runtime, and the migration operator identity are not acceptable substitutes.

Migration recovery has two coherent phases for its active path. In the closed phase, the operator runtime, normalizer authority, managed-QC1 authority, and managed execution are all disabled. In the executable phase, all four are enabled. Mixed phases are rejected. The executable phase requires new deployment hashes plus exact read-only infrastructure and IAM readback before any recovery call.

The migration regrader is excluded from both normalization/QC1 phases and has its own disabled-by-default authority boundary. The signed regrade-intent and processor-finalization contracts do not make that runtime available by themselves. Enable it only when capabilities advertise the separately pinned authority, grader, storage, KMS, and finalization releases; do not route regrading through the normalization or managed-QC1 identities.

Normalization and managed GPT-5.6 Luna execution are separate active-path operations. Regrading remains unavailable unless its distinct signed-intent, grader, and processor-finalization capabilities are all advertised. A retained output may then be regraded only with its exact rubric and verifier or a policy-approved judge-dominant replacement. A missing primary output requires a fresh managed Modal/Harbor QC1 rollout on the exact revision and native harness. Managed execution is asynchronous: an idempotent ensure operation is observed through bounded status reads and may return a canonical bundle only after a terminal success. If approved tooling cannot produce the canonical bundle and managed-execution approval, the task remains blocked; an operator may not edit the migration report or database to make it review-ready.

Before switching the active catalog, operators must review immutable JSON, CSV, and human-readable migration reports. They must validate exactly one canonical finance, LuminAI healthcare, Engram biology, legal, hardware, and code canary. Every candidate must have complete Master evidence, all six forensic sections, a reconciled criterion ledger, verified artifacts, an exact retained canonical source ZIP generation, and current publication and execution authority.

A receipt manifest must resolve every staging receipt by ID and hash. A first-time regrade requires both its original and regenerated receipts. Before cutover, Audit materializes and verifies the exact proposed revision, memberships, rollout admissions, compatibility candidates, and catalog head. The catalog switch is one compare-and-swap to that immutable benchmark revision. After the switch, Audit re-reads the selected head, revision, membership and admission roots, compatibility projections, and artifacts. Any stale authority, missing field, unresolved task, failed domain canary, or unavailable rollback procedure blocks cutover.

The internal `gdpx:orchestrate-migration` command builds a hash-bound dry-run plan and immutable JSON, CSV, and Markdown reports. Apply mode accepts only the exact plan and migration-report hash. It invokes the internal staging service for each generation-bound candidate and emits a hash-bound receipt manifest. It never switches the catalog.

Use the receipt manifest to build a fresh live snapshot and final migration report. `gdpx:verify-migration-candidate` materializes the exact proposed release through capture-only write ports and proves it before the catalog compare-and-swap. `gdpx:verify-migration-canaries` validates the six named canonical domain bundles. `gdpx:verify-current-release` performs the final read-only check against the exact active v3 catalog. It revalidates the committed membership and rollout-admission roots, membership-bound readiness attestations, every admitted rollout, and each artifact's bound generation, size, and SHA-256. A release requires passing reports with zero missing fields. These commands do not repair evidence or replace same-tenant, anonymous, and cross-tenant HTTP authorization tests.

Before cutover, generate and retain a `gdpx:rollback-catalog` plan for the exact current and previous head. Applying it requires the exact plan SHA-256 plus the unchanged expected current revision and generation. Rollback revalidates the target revision under current policy and performs a compare-and-swap; it has no force mode and does not erase the rejected revision.
