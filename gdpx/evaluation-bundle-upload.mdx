`POST /api/v3/gdpx-submissions` accepts an API bundle, not an unchanged [GDPx repository folder](/gdpx/quickstart).

Repository `TASK.json`, lowercase `run.json`, and `traces/` are source records. The API uses strict control documents and an `evaluations/` tree. Renaming or zipping the source files does not perform this mapping.

## Discover the contract

Use one origin and a tenant-scoped key:

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/capabilities" \
  --output gdpx-capabilities.json

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/schemas/review-bundle" \
  --output gdpx-review-bundle.schema.json
```

Check `access.can_submit`, `admission.can_submit`, required scopes, modes, adapters, schema links, and archive limits. Follow the advertised schema relation if it changes. The schema response is a descriptor containing control-file schemas and binding rules, not one schema to apply blindly to every file.

Creation and upload require `uploads:write` and `imports:write`; task readback requires `tasks:read`. Neither `/v1/whoami` nor v2 intake readiness is the v3 admission gate.

The currently advertised adapters are `canonical` and `legacy_snapshot`. There is no advertised adapter for uploading the GDPx repository export unchanged. A legacy snapshot is a draft path, not a shortcut to complete canonical evidence.

## Choose the mode

| Mode | Bundle contents | Result |
| --- | --- | --- |
| `audit_task_draft` | Canonical task or supported legacy snapshot; no evaluation | Retained blocked draft for review |
| `task_and_evidence` | Complete canonical tasks; one evaluation and one rollout per task | Evidence-catalog admission candidate |
| `evidence_only` | One evaluation and rollout for one exact retained canonical revision | Evidence candidate for that revision |

Use the separately advertised draft contract and `audit_only` policy for `audit_task_draft`. A legacy snapshot needs canonical normalization before it can receive qualifying evidence.

Under `gdpx-review-bundle/1.1.0`, a `task_and_evidence` bundle can contain 1–100 tasks. `evidence_only` targets one task. These are API submission limits, not limits on the number of runs or trials retained in the repository.

A later attempt does not replace immutable task bytes or become current automatically. Follow Standard Data's admission plan for attaching evidence and campaign mapping.

## Canonical ZIP layout

```text
GDPX_BUNDLE.json
tasks/<task_id>/
├── TASK.json
├── PUBLICATION_AUTHORITY.json
└── <inventoried task and workspace files>
evaluations/<task_id>/<run_id>/
├── RUN.json
└── <rollout_id>/
    ├── ROLLOUT.json
    ├── trajectory.atif.json
    ├── verifier.json
    ├── criterion-decisions.json
    └── artifacts/
```

Put `GDPX_BUNDLE.json` at the ZIP root, without an extra enclosing folder. Validate against the fetched control-file schemas.

| Control file | What to bind |
| --- | --- |
| `GDPX_BUNDLE.json` | Every other retained member's path, byte size, media type, SHA-256, and task/run/rollout association; exclude the manifest itself |
| Canonical `TASK.json` | Exact prompt, rubric, verifier, task-content hash, and complete workspace inventory with visibility |
| `PUBLICATION_AUTHORITY.json` | Source rights and publication declaration for the exact task and delivery |
| `RUN.json` / `ROLLOUT.json` | Canonical task, run, and rollout identities, execution settings, and evidence bindings |
| Evidence files | Observable trajectory, final answer, native work products, verifier output, every criterion decision, and score reconciliation |

Do not copy repository `TASK.json.runs` or add `rollouts` to canonical `TASK.json`. Keep evaluation records under `evaluations/`. An image digest, directory hash, or file count is not a complete workspace inventory.

Preserve source-to-canonical identity mappings and original task bytes. An adapter cannot invent missing traces, criterion decisions, artifacts, or managed-execution proof. Exclude private reasoning, credentials, signed URLs, and provider-private payloads.

A direct canonical review bundle requires hash-bound publication authority matched to the active rights record. It does not grant managed-execution approval or replace QC4.

## Create, upload, and poll

Use the exact ZIP metadata and advertised contract:

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/api/v3/gdpx-submissions" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: gdpx-<stable-client-operation-id>" \
  --data '{
    "filename": "delivery.zip",
    "content_type": "application/zip",
    "size_bytes": 123456,
    "sha256": "<64-lowercase-hex>",
    "contract_version": "gdpx-review-bundle/1.1.0",
    "mode": "task_and_evidence",
    "target_task_revision_id": null,
    "adapter_mode": "canonical",
    "publication_policy": "publish_when_review_ready"
  }' \
  --output gdpx-submission.json
```

Replace the example size and hash with the actual ZIP values. For `evidence_only`, set the exact target revision; for a draft, use its separate contract and policy.

1. Follow the returned upload relations, including part signing/finalization when required.
2. Send storage only the headers provided for that upload—never the API bearer key.
3. Complete the upload through the returned API relation.
4. Poll the submission's `self` relation to a terminal state.

Keep the same idempotency key for retries of the same create operation. Retain the submission ID, ZIP hash, contract, mode, state, and blocker/warning codes and pointers. A corrected bundle is a new immutable submission.

## Interpret admission

An accepted upload is not a QC pass. If one task blocks a multi-task cohort, the active catalog does not change for that cohort; diagnostic source and blocker records may still be retained.

Check `managed_execution_trust.managed_qc1_execution.available` and its blocker before promising managed QC1 completion. Storage acceptance alone does not establish execution trust.

A draft in **Review Tasks** may remain blocked. `review_ready` describes API technical readiness; active catalog membership selects evidence for readback. Neither certifies the separate QC2–QC4 [program decisions](/qc-stages-for-benchmark).

## Verify readback

```text
GET /api/v3/tasks/{task_revision_id}/review-readiness
GET /api/v3/tasks/{task_revision_id}/runs/{run_id}/rollouts/{rollout_id}
GET /api/v3/gdpx/catalog/current
```

Confirm that task, run, rollout, score, and artifact identities match the submitted evidence. The external rollout route is not a pre-admission preview: a candidate outside the active catalog can return `404`. Inspect the submission and blockers first.

Use the [legacy v2 draft flow](/gdpx/import-approved-tasks) only when explicitly requested. It is not an alternative way to bypass v3 admission.
