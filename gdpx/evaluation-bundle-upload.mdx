Use `POST /api/v3/gdpx-submissions` for canonical GDPx drafts and active evidence-catalog candidates. Do not send an unconverted partner source handoff to this endpoint unless the live capability response advertises and Standard Data confirms the matching adapter.

<Warning>
  A successful upload is not a passed QC stage or inclusion in the released GDPx benchmark. Audit may retain a blocked record for diagnosis. Wilderness **Review Tasks** and **Results** represent different states.
</Warning>

## Discover the live contract

Use one API origin and a tenant-scoped key:

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/capabilities" \
  --output gdpx-capabilities.json
```

The v3 capability response is the authority for:

- `access.can_submit` and `admission.can_submit`;
- accepted modes and contract versions;
- schema links;
- adapter modes;
- upload and archive limits; and
- `managed_execution_trust.managed_qc1_execution.available` and its blocker.

Do not use `/v1/whoami` or the v2 intake state as a v3 admission gate. Those fields describe the legacy v2 workflow.

Fetch the schema relation returned by capabilities. The static path below is valid only when the response advertises it:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/schemas/review-bundle" \
  --output gdpx-review-bundle.schema.json
```

Creating and completing a submission requires the scopes returned by the service, typically `uploads:write` and `imports:write`. Readback typically requires `tasks:read`.

If `managed_qc1_execution.available` is false, the service may still accept and retain a draft or evidence bundle. You cannot promise end-to-end QC1 completion or active evidence-catalog admission until the blocker is resolved.

## Choose a mode

| Mode | Use it when | Evidence in the ZIP | Expected result |
| --- | --- | --- | --- |
| `audit_task_draft` | You have an exact canonical task, or a supported legacy snapshot, but no complete QC1 attempt | No evaluation | Immutable blocked draft; may appear in **Review Tasks** |
| `task_and_evidence` | You have complete task source and one admission attempt for each task | One evaluation and one rollout per task | Active evidence-catalog candidate; not a final benchmark-release decision |
| `evidence_only` | You are attaching first QC1 evidence to an exact retained canonical draft, or one later attempt to a retained revision | One evaluation and one rollout for one task revision | Immutable evidence candidate |

An `audit_task_draft` submission is intentionally blocked. A canonical draft can later receive its first QC1 attempt through `evidence_only`. A legacy-snapshot draft must first be replaced by a complete canonical task definition.

For the same byte-identical retained canonical revision, `evidence_only` freezes one later attempt candidate without replacing the existing task bytes or qualifying anchor. A separate operator admission is required before that candidate can become current.

## Canonical ZIP layout

When the service advertises `gdpx-review-bundle/1.1.0`, a canonical review bundle follows this outline:

```text
GDPX_BUNDLE.json
tasks/
└── <task_id>/
    ├── TASK.json
    ├── PUBLICATION_AUTHORITY.json
    └── <inventoried task and workspace files>
evaluations/
└── <task_id>/
    └── <run_id>/
        ├── RUN.json
        └── <rollout_id>/
            ├── ROLLOUT.json
            ├── trajectory.atif.json
            ├── verifier.json
            ├── criterion-decisions.json
            └── artifacts/
```

Do not wrap this canonical layout in an extra batch directory. `GDPX_BUNDLE.json` belongs at the ZIP root.

The live JSON Schema defines every required field. The following rules prevent the most common format errors.

### `GDPX_BUNDLE.json`

Inventory every other retained ZIP member. Record the path, byte size, media type, and SHA-256 required by the schema. Bind each task, run, rollout, and artifact to its exact identifier.

Do not inventory `GDPX_BUNDLE.json` itself.

### Canonical `TASK.json`

Describe the immutable task, exact prompt, rubric, verifier, task-content hash, and complete workspace inventory.

Do not add a `rollouts` field. Canonical `TASK.json` is strict. Runs and rollouts belong under `evaluations/` in `RUN.json` and `ROLLOUT.json`.

Every workspace file must use the path, hash, size, media type, artifact kind, and visibility required by the fetched schema. A directory hash, image digest, file count, or path list is not a complete workspace inventory.

### `PUBLICATION_AUTHORITY.json`

Include the source-side rights and publication declaration in every direct canonical review bundle. Bind it to the exact task and source delivery. Keep it outside the agent runtime.

A separate Audit-draft or adapter contract may retain a blocked archive without this file when its live schema permits that case. For a direct canonical review bundle, the file is required, hash-bound, and matched to Standard Data's active rights record before catalog membership. It does not approve managed execution or replace Standard Data's QC4 release review.

### Evaluation evidence

For every rollout, include:

- one `RUN.json` and `ROLLOUT.json` with consistent task, run, and rollout identities;
- a complete observable trajectory;
- the final answer and native work products;
- verifier and per-test output;
- exactly one decision for every rubric criterion;
- score aggregation, threshold, outcome, and reconciliation; and
- declared artifacts with matching paths, sizes, media types, and hashes.

Do not include private reasoning, actual credentials, signed URLs, or provider-private payloads.

## Keep submission and evaluation counts separate

Under `gdpx-review-bundle/1.1.0`:

- a `task_and_evidence` ZIP can declare 1–100 unique tasks;
- each declared task has exactly one evaluation and one rollout in that ZIP;
- an `evidence_only` ZIP targets one retained task revision with one evaluation and one rollout; and
- one blocked declared task prevents the active evidence catalog from changing for the admission cohort.

Audit may still retain immutable source, evidence, and blocker records from a blocked cohort. The active evidence-catalog update is cohort-atomic; diagnostic retention is not rolled back.

A QC3 campaign can require many attempts. Standard Data owns QC3 ingestion and campaign mapping. Partners preserve the complete native corpus and submit individual attempts through `evidence_only` only when an operator provides the target revision and admission plan. The current API does not natively label a run as QC3. Do not place the complete QC3 corpus in `TASK.json` or add several attempts for one task to a single v1.1 review bundle.

## Adapter submissions

An adapter is valid only when the live capability response advertises it and Standard Data confirms that it matches the delivered source revision.

Adapters may:

- preserve native source paths and bytes;
- map existing task, run, rollout, and artifact fields;
- return a preview or crosswalk; and
- normalize supported evidence into the canonical record.

Adapters may not:

- invent missing trajectories or work products;
- infer verifier or criterion decisions that were never retained;
- turn a truncated export into complete evidence;
- repair a mislabeled model or task silently; or
- grant QC, readiness, or active evidence-catalog status.

Large native archives may need to be split to satisfy the current capability-advertised compressed, member, and expanded-size limits.

## Create the submission

Use only values advertised by the live capability response:

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/api/v3/gdpx-submissions" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: gdpx-<stable-client-operation-id>" \
  --data '{
    "filename": "delivery.zip",
    "content_type": "application/zip",
    "size_bytes": 123456,
    "sha256": "<64-lowercase-hex>",
    "contract_version": "gdpx-review-bundle/1.1.0",
    "mode": "task_and_evidence",
    "target_task_revision_id": null,
    "adapter_mode": "canonical",
    "publication_policy": "publish_when_review_ready"
  }' \
  --output gdpx-submission.json
```

The values above illustrate a v1.1 `task_and_evidence` request. Replace them with the current advertised contract and your exact ZIP metadata.

For `evidence_only`, set the exact `target_task_revision_id`. For `audit_task_draft`, use the separately advertised draft contract and policy.

## Upload and poll

Follow the relations in the create response:

1. upload the exact bytes through the returned storage relation;
2. send only the storage headers returned for that relation;
3. complete the upload through the returned API relation; and
4. poll the returned `self` relation until the submission reaches a terminal state.

Do not construct storage URLs. Do not send the Standard Data bearer key to object storage.

Retain:

- the submission ID;
- source ZIP size and SHA-256;
- contract, mode, and adapter;
- terminal state; and
- every blocker or warning code and JSON pointer.

Correct a blocked source package and create a new immutable submission. Do not claim that the earlier record changed in place.

## Interpret the result

| Result | Interpretation |
| --- | --- |
| Draft visible in **Review Tasks** | Audit retained a blocked draft |
| Submission retained with blockers | Source or evidence is available for diagnosis; the active evidence catalog did not change |
| `review_ready` | Current v3 technical readiness is satisfied |
| Task in active evidence catalog and rollout readable | Audit selected that immutable record; this alone is not inclusion in the released GDPx benchmark |
| QC2–QC4 complete in tracker | Standard Data completed the remaining program reviews |

The API does not currently expose native QC2, QC3, or QC4 states. Do not infer those stages from `review_ready` or catalog membership.

## Verify exact readback

For a record already selected by the active evidence catalog for Wilderness **Results**, check:

```text
GET /api/v3/tasks/{task_revision_id}/review-readiness
GET /api/v3/tasks/{task_revision_id}/runs/{run_id}/rollouts/{rollout_id}
GET /api/v3/gdpx/catalog/current
```

The external rollout route is not a general pre-admission preview. A retained candidate that is not selected by the active evidence catalog normally returns `404`; inspect the submission and its blockers instead.

Confirm that the returned task, run, rollout, score, evidence, and artifact identities match the submitted bytes. Then check the separate benchmark review record for QC2–QC4 completion.

## Legacy v2

`POST /api/v2/workspace-submissions` creates legacy draft revisions only. It cannot add a task to the active evidence catalog or certify any QC stage. Use it only when Standard Data explicitly directs you to the [legacy draft import](/gdpx/import-approved-tasks).
