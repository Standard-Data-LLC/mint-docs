`POST /api/v3/gdpx-submissions` is the only submission path that can publish a task into the GDPx/Wilderness catalog. It accepts a ZIP that binds runnable task bytes, rollout evidence, criterion decisions, and review artifacts into one immutable delivery.

<Warning>
  A successful byte upload is not publication. A task appears in Wilderness only after managed execution approval, current-policy `review_ready` status, and inclusion in the active catalog revision. A task with missing or irreconcilable evidence remains in Audit as `blocked` and is not included in the active GDPx catalog.
</Warning>

The legacy `/api/v2/workspace-submissions` workflow may still create draft Audit revisions. It cannot add a task to the GDPx benchmark revision or Wilderness catalog.

## Authenticate and discover the contract

Use the shared Standard Data API origin and a tenant-scoped key:

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"
```

Read capabilities and the current JSON Schema before building a bundle:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/capabilities" \
  --output gdpx-capabilities.json

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/schemas/review-bundle" \
  --output gdpx-review-bundle.schema.json
```

Creating a submission requires `uploads:write` and `imports:write`. Capabilities, schema, catalog, readiness, submission-status, and rollout reads require `tasks:read`. Authentication is always tenant-bound.

The current schema identifier is `https://standard-data.dev/contracts/gdpx-review-bundle/1.1.0/schema.json`.

The capability response is authoritative for the active contract version, maximum ZIP size, supported adapter modes, publication policy, and resumable-upload limits. Do not hard-code those values from an older response.

<Warning>
  Submission is fail-closed. Offer an upload action only when `/v1/whoami` reports `canonical_submission.state` as `ready` **and** `/api/v3/gdpx/capabilities` reports `access.can_submit` as `true`. Inspect `admission.blockers` when it is false. During a controlled rollout, admission may be disabled or tenant-allowlisted even though the schema and read APIs are reachable.
</Warning>

## Canonical ZIP layout

The canonical contract version is `gdpx-review-bundle/1.1.0`. Each ZIP contains exactly one task, one QC1 run, and one rollout:

```text
GDPX_BUNDLE.json
INTERNAL_QA_CREDENTIAL_ATTESTATION.json   # internal-QA deliveries only
tasks/
└── <task_id>/
    ├── TASK.json
    ├── PUBLICATION_AUTHORITY.json
    ├── task.toml
    ├── instruction.md
    ├── environment/
    ├── tests/
    └── solution/
evaluations/
└── <task_id>/
    └── <run_id>/
        ├── RUN.json
        └── <rollout_id>/
            ├── ROLLOUT.json
            ├── trajectory.atif.json
            ├── verifier.json
            ├── criterion-decisions.json
            └── artifacts/
```

`GDPX_BUNDLE.json` is a complete inventory. For every retained file, record its normalized relative path, byte size, media type, and SHA-256. It binds the one task, one run, and one rollout to their exact `task_revision_id`, `run_id`, and `rollout_id`. A multi-task or multi-rollout ZIP is invalid; create one immutable submission per task attempt.

`TASK.json` uses `gdpx-task/1.1.0`. It binds the exact prompt, rubric, verifier, `task_content_sha256`, and a complete `workspace_files` inventory. Each workspace entry declares its normalized path, SHA-256, byte size, media type, artifact kind, and visibility. `environment.workspace_inventory_sha256` covers the sorted inventory, including every one of those fields. `RUN.json` uses `gdpx-run/1.1.0` and must repeat the same workspace-inventory binding. The derived Master projection uses `gdpx-master-evidence/1.1.0` and binds that inventory again.

<Warning>
  Do not treat an environment directory hash, image digest, file count, or list of paths as a workspace inventory. Every agent-visible, tool-mediated, verifier-only, and publication-only task file must appear with its exact path, hash, size, media type, kind, and visibility.
</Warning>

### Uploaded publication declaration

Every task submitted with `publication_policy: "publish_when_review_ready"` must include `tasks/<task_id>/PUBLICATION_AUTHORITY.json` using `gdpx-publication-authority/1.1.0`. The bundle manifest records that file with role `publication_authority` and binds its path and SHA-256 from the task descriptor. Missing, blocked, mismatched, or tampered declaration evidence is a publication blocker even when every technical evaluation check passes.

The partner-uploaded declaration binds the exact task, task-content hash, workspace-inventory hash, logical task, source delivery, rights basis, agreement status, owner intent, and source mappings. Its self-attestation hash covers the canonical JSON record. An external-catalog declaration must state `publication_target: "external_catalog"`, set `intended_catalog_member: true`, carry an applicable executed-agreement or first-party rights basis, and include approval scoped to `gdpx_benchmark_qc_and_publication`.

The uploaded declaration is necessary but not sufficient. Audit separately requires an immutable publication-rights grant in Standard Data's operator-controlled registry and an active authority head that resolves to that grant. The grant and head bind the exact declaration, source delivery, task-content hash, and workspace-inventory hash. Submission credentials cannot create, replace, or advance either record.

If the active policy changes or an owner revokes publication, Audit first publishes a replacement catalog revision that excludes the task, then advances the authority head to the new immutable decision. The old grant, head revision, benchmark membership, task, and evidence remain in history. The current readiness projection becomes blocked. Audit never silently rewrites the old benchmark membership or makes the active catalog unavailable during revocation.

<Warning>
  Upload permission is not publication authority. A valid API key, successful transport, complete rollout, partner declaration, self-hash, or technical candidate cannot substitute for a task-bound declaration, matching immutable operator grant, and current authority head. Never reuse an authority file across revisions or deliveries.
</Warning>

### Internal-QA exact-byte fixture retention

Use the internal-QA path only when an isolated benchmark world intentionally contains credential-like fixture literals that reviewers must inspect byte for byte. It is not a general secret-scanner exception.

The declaration must state `publication_target: "internal_qa"`, set `intended_catalog_member: false`, use a first-party rights basis, and include approval scoped to `gdpx_internal_qa_synthetic_fixture_retention`. Standard Data separately retains an operator-controlled `INTERNAL_QA_CREDENTIAL_STATEMENT.json` using `gdpx-internal-qa-credential-statement/1.0.0`. Its semantic statement hash, exact file hash, immutable control object, active grant, and authority-head generation are distinct bindings; an uploader cannot create or advance them.

The review bundle includes `INTERNAL_QA_CREDENTIAL_ATTESTATION.json` and inventories it in `GDPX_BUNDLE.json` with role `internal_qa_credential_attestation`. The attestation must include:

- a complete, sorted, hash-bound corpus covering every retained and projected credential-like occurrence;
- exactly one source-bound classification for every detector match;
- `synthetic_fixture_literal` records with exact source, fixture, and Master pointers and hashes, offline-world provenance, isolated execution, disabled network egress, and no environment, secret-manager, or provider origin;
- `non_value_syntax` records with parser proof for identifiers, expressions, and empty literals; and
- clean high-confidence, provider-format, and grouped-token entropy scans plus a `network_origin` verdict of `offline_only` over the same corpus hash.

Source and Master bytes must match the attested fixture bytes exactly. Placeholders, rewritten values, an incomplete corpus, an uncited match, or a blanket `internal` or `sanitized` flag blocks admission. Any byte, corpus, authority, or grant change requires a new statement, attestation, operator grant, and exact replay.

Internal-QA evidence may run through managed execution and remains readable to every authenticated tenant user with `tasks:read` while its exact active grant is valid. It never satisfies external-catalog readiness or membership. Revoking or replacing the grant closes every internal-QA review path without deleting immutable audit history.

An internal-QA admission writes only the immutable V3 review binding, admission terminal, exact access reservation, Master evidence, criterion chunks, and artifact bindings. It must not create a V2 task projection, workspace, supplied run, readiness attestation, family, data sheet, or catalog record. Legacy V2 records found for a review-only revision are stale migration artifacts and must remain excluded from every reader until an operator reviews the dry-run inventory.

### Managed execution and approval

An uploaded `RUN.json`, provider result, Harbor identifier, runtime receipt, or field that claims execution validation is evidence supplied by the uploader. It cannot authenticate its own execution.

A rollout qualifies for QC1 publication only after Standard Data runs or verifies it through the approved managed execution path. The retained runtime receipt binds the exact task and workspace, run and rollout manifests, trajectory, verifier output, criterion ledger, work products, forensic sections, runtime configuration, harness result, logs, and immutable artifact hashes. After the evidence generations, Master, criterion chunks, and artifacts commit, Audit verifies their exact hashes and creates a separate operator-authenticated managed-execution approval for those canonical bytes.

The approval is not part of the uploaded authority declaration and cannot be created by submission credentials. Until the exact approval exists and verifies, the run remains `not_execution_validated`. Audit keeps the first import as archive evidence, but it cannot satisfy QC1, become `review_ready`, enter Wilderness Results, or support catalog membership. After approval, replay or resubmit the exact hash-bound bundle when the capability response instructs you to do so; any byte change requires new verification and approval.

If trusted-runtime attestation is rejected before model launch, retain only bounded structural diagnostics: `missing_marker`, `duplicate_marker`, `marker_not_first`, `malformed_marker`, `missing_sidecar`, `malformed_sidecar`, `mismatched_sidecar_a`, `controller_timeout`, or `controller_terminated`; marker count and first-line status; capped stdout and stderr line and byte counts with truncation flags; whether a chunk was observed; return code when available; elapsed time; and sidecar presence and validity. Never retain raw stdout, stderr, marker values, or sidecar bytes in this diagnostic. A pre-launch rejection produces no subject rollout, no score, and no QC1 credit. Display it as an execution rejection, never as score `0`.

Large trajectories and work products stay as hash-bound objects. Do not copy them into a metadata field or replace them with a summary.

### Required rollout evidence

Each rollout must retain:

- the exact prompt and relevant agent-visible context;
- an ordered observable trajectory with model messages, tool calls, tool results, environment events, and errors;
- the final model answer or primary work product;
- verifier output and all test results;
- a decision for every scored rubric criterion;
- score reconciliation, including aggregation, threshold, dependencies, and hard gates;
- model, harness, environment, verifier, and judge versions;
- duration, turns or steps, token usage, cost, stop condition, and execution outcome when supplied by the harness; and
- immutable artifact hashes and object generations.

The six forensic sections—Problem, Setup Logs, Agent Logs, Results, Test Logs, and Grading—must be present. A section with no applicable source data must use an explicit `not_applicable` status and a reason. Omitting a section is not equivalent to `not_applicable`.

### Criterion decisions

Each item in `criterion-decisions.json` must contain:

| Field | Requirement |
| --- | --- |
| `criterion_id` | Stable ID that exactly matches one source-rubric criterion |
| `source_text` | Exact source wording; do not paraphrase the grading contract |
| `status` | `passed`, `failed`, `partial`, `blocked`, `not_applicable`, or `unscored` |
| `weight` | Source weight or scoring contribution when one exists |
| `awarded_contribution` / `maximum_contribution` | Awarded and possible contribution when applicable |
| `direct_result` | Result before dependency or hard-gate effects |
| `cascaded_result` | Result after dependency or hard-gate effects |
| `dependency_criterion_ids` | Exact IDs of criteria that can cascade into this result |
| `grader` | Verifier or judge identity and pinned version |
| `rationale` | Human-readable explanation grounded in observable evidence |
| `evidence_refs` | Typed references to retained events, tests, outputs, or artifacts |

The score-reconciliation object records the aggregation rule, reported score, calculated score, pass threshold, hard-gate results, and whether the values reconcile. A duplicate criterion ID, unknown criterion, dangling evidence reference, or unexplained score mismatch blocks publication.

## Create a submission

Hash the exact ZIP and send one idempotent request:

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/api/v3/gdpx-submissions" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: gdpx-<stable-client-operation-id>" \
  --data '{
    "filename": "delivery.zip",
    "content_type": "application/zip",
    "size_bytes": 123456,
    "sha256": "<64-lowercase-hex>",
    "contract_version": "gdpx-review-bundle/1.1.0",
    "mode": "task_and_evidence",
    "target_task_revision_id": null,
    "adapter_mode": "canonical",
    "publication_policy": "publish_when_review_ready"
  }' \
  --output gdpx-submission.json
```

Request fields:

| Field | Accepted value |
| --- | --- |
| `content_type` | `application/zip` |
| `contract_version` | `gdpx-review-bundle/1.1.0` |
| `mode` | `task_and_evidence` or `evidence_only` |
| `target_task_revision_id` | Required for `evidence_only`; otherwise `null` |
| `adapter_mode` | `canonical` or `terra_compatibility` |
| `publication_policy` | `publish_when_review_ready` |

The response returns `gdpx_submission_id` plus same-origin relations for upload authorization, completion, polling, and cancellation. Upload signing and finalization reuse the v2 upload-session transport linked by the response. Follow those links. Do not construct storage URLs, persist resumable-session credentials, or send the Standard Data API key to object storage.

### Evidence-only submissions

Use `mode: "evidence_only"` only to attach one run and one rollout to a task revision that Audit already retains. Set `target_task_revision_id` to that exact revision. The submitted `TASK.json`, task-content hash, full workspace inventory, rubric, verifier, and environment bindings must exactly match the retained canonical task.

An evidence-only submission never changes the task head, replaces task bytes, or creates a new task revision. Any mismatch blocks the submission. If the task changed, submit a new `task_and_evidence` bundle for the new immutable revision.

## Follow the workflow

```text
awaiting_upload → sanitizing → normalizing → validating → importing → review_ready
                                                                  └→ blocked
```

Poll `GET /api/v3/gdpx-submissions/{gdpx_submission_id}` or the returned `self` link. `blocked` is terminal for that immutable submission. Cancellation also ends in `blocked` with reason code `SUBMISSION_CANCELLED`; it does not introduce a separate workflow state. Correct a blocked source package and create a new submission. The result includes stable issue codes and JSON pointers to missing, mismatched, or unsafe fields.

Validation is all-or-nothing for publication. It verifies identity bindings, task and workspace hashes, publication declaration, active rights grant and head, managed-execution approval, artifact availability, rubric completeness, criterion evidence, score reconciliation, runtime status, secret scanning, and omission of private reasoning.

The complete publication sequence is:

```text
v3 submission and archive-only import
  → managed QC1 run and retained runtime receipt
  → server verification of committed evidence generations
  → immutable operator-authenticated managed-execution approval
  → exact bundle replay or resubmission when advertised
  → current-policy review-readiness attestation
  → immutable benchmark-revision membership
  → active GDPx catalog head
```

### Catalog admission and reader activation

`review_ready` is an immutable attestation for one exact task revision, qualifying rollout, Master projection, and policy version. It does not make a task visible by itself. Audit copies that exact readiness binding into an immutable benchmark-revision membership, then advances the active GDPx catalog head to the complete benchmark revision.

Any compatibility projection used by older readers is prepared and hash-verified before publication, but remains hidden. Audit activates it only after the active v3 catalog admits the same task revision, run, rollout, Master hash, and evidence hash. A partial write therefore cannot expose a score without its Master evidence. Retrying an interrupted activation reuses the retained immutable authorization and completion bindings; it does not mint a different rollout or mutate the historical membership.

The GDPx tab reads `GET /api/v3/gdpx/catalog/current`. It does not infer membership from publication flags, creator labels, run counts, legacy stage labels, or a mutable `is_current` field.

`review_ready` always means ready under the policy recorded by that attestation. A historical readiness attestation remains immutable, but a changed rights head, revoked authorization, mismatched execution approval, or newer policy makes it non-current and removes publication eligibility until Audit issues new matching records and a new benchmark revision becomes active.

After import, verify the exact task revision:

```text
GET /api/v3/tasks/{task_revision_id}/review-readiness
GET /api/v3/tasks/{task_revision_id}/runs/{run_id}/rollouts/{rollout_id}
GET /api/v3/gdpx/catalog/current
```

The active catalog is the immutable benchmark revision selected by that durable catalog head.

<Warning>
  GDPx publication is not a temporary preview. Submit only task revisions intended to remain in the tenant's benchmark history. Corrections create a new immutable revision for the same logical task. The public v3 API does not delete evidence or change publication authority; an operator-controlled revocation excludes a task through a new head and catalog revision without erasing history.
</Warning>

## Terra compatibility mode

Choose `terra_compatibility` only for a legacy or partner-specific package that cannot be emitted canonically **and** only when the current capabilities response lists `terra_compatibility` in `adapter_modes`. If the server does not advertise that adapter, submit a canonical bundle or wait for the trusted adapter to become available; never emulate the adapter client-side. The capabilities response and fetched schema—not this page or a cached client copy—are authoritative for availability and accepted fields.

When advertised, the pinned compatibility model may identify source files, map heterogeneous fields, assign source-derived stable IDs, and create citation-bound presentation summaries. Its exact model revision, adapter prompt version, and release are recorded in the normalized evidence. The public contract does not permit callers to select or substitute a model.

Terra must not:

- rewrite task instructions or rubric meaning;
- change weights, thresholds, dependencies, or hard gates;
- invent a prompt, output, test, grading decision, or evidence;
- infer missing facts from domain knowledge; or
- authoritatively rescore the rollout.

Every generated field records source locations, input and output hashes, model revision, adapter prompt version, and timestamp. An ambiguous or uncited mapping blocks publication.

If an exact rubric and final output exist but the criterion ledger is absent, rerun the original verifier or judge against the retained output. A policy-approved stronger compatible judge may be used under the judge-dominance rule, but the result must be labeled as regrading. Preserve both scores and block publication for adjudication if they disagree.

## Legacy migration and reruns

For existing tasks, recover evidence in this order:

1. canonical retained Audit evidence;
2. reviewer-evidence companions;
3. immutable release artifacts; and
4. the original partner delivery.

A derived Master projection must cite those retained sources and record the transformer version. It may improve presentation, but it may not invent missing primary evidence.

Regrade a retained final output when the source rubric and verifier are available. Run a fresh GPT-5.6 Luna QC1 rollout only when primary evidence cannot be recovered or the task revision changed. Bind a rerun to the exact immutable revision and native harness; do not use a new run to overwrite historical evidence.

### Operator migration boundary

There is no public batch-migration endpoint. A migration inventory or report does not import evidence, approve execution, establish current readiness, or publish a catalog. Operators recover each exact task/run/rollout from canonical Audit evidence, reviewer companions, immutable release artifacts, and the original partner delivery—in that order—then submit complete canonical v3 bundles through the same admission path described above.

Recovery, verifier regrading, and managed GPT-5.6 Luna execution are separate operations. A retained output may be regraded only with its exact rubric and verifier or a policy-approved judge-dominant replacement. A missing primary output requires a fresh managed Modal/Harbor QC1 rollout on the exact revision and native harness. If approved tooling cannot produce the canonical bundle and managed-execution approval, the task remains blocked; an operator may not edit the migration report or database to make it review-ready.

Before switching the active catalog, operators must review immutable JSON, CSV, and human-readable migration reports; validate finance, LuminAI healthcare, Engram biology, legal, hardware, and code canaries; and prove that every candidate has complete Master evidence, all six forensic sections, a reconciled criterion ledger, verified artifacts, and current publication and execution authority. The catalog switch is one compare-and-swap to a new immutable benchmark revision. Any stale authority, missing field, unresolved task, or unavailable rollback procedure blocks cutover.

The internal `gdpx:verify-current-release` command performs the final read-only data check against the exact active V3 catalog. It revalidates the committed membership root and current readiness records, reads every admitted rollout, and re-reads each artifact at its bound generation to verify its size and SHA-256. A release requires a passing JSON/CSV/Markdown report with zero missing fields. This command does not repair data, publish a catalog, or replace authenticated same-tenant, anonymous, and cross-tenant HTTP authorization tests.

<Warning>
  The legacy v39 backfill command is inventory-only and cannot publish evidence or switch the GDPx catalog. The current internal migration reporter can publish only a cohort that is already current-policy `review_ready`; it does not reconstruct evidence, rerun a verifier, or schedule Modal/Harbor work.
</Warning>
