Wilderness collects runnable benchmark tasks for standardized rollouts and scaled evaluation. The canonical submission API accepts one workspace ZIP, sanitizes and maps it, runs the pinned v15 static admission policy against every mapped task, and creates immutable task revisions automatically when the complete workspace is eligible.

<Warning>
  This is a durable workflow, not document feedback. A successful `/v1/evaluate` response—including `ready_to_submit: true`—never authorizes the ZIP. Only the v15 workspace preflight can make this submission eligible for automatic import.
</Warning>

There is no hidden customer approval step. Availability is expressed by the authenticated capability endpoint and the global service mode.

## Configure one API origin and key

```bash
export STANDARD_DATA_API_BASE="https://<standard-data-api-host>"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"
```

The same key may call `/v1` document feedback and `/api/v2` canonical submission. Workspace submission requires `uploads:write`, `imports:write`, and `tasks:read` in addition to the evaluation scopes.

<Note>
  Store long-lived customer keys in a managed secret store such as Google Secret Manager, AWS Secrets Manager, Azure Key Vault, or a server-side encrypted credential vault. Inject them at runtime. Never commit them, paste them into task archives, include them in logs, or store them in browser `localStorage`. Wilderness browser sessions use short-lived Firebase credentials instead of customer API keys.
</Note>

## 1. Check intake readiness

Do this before showing a file picker or attempting a mutation:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v2/intake-capabilities" \
  --output intake-capabilities.json
```

The response state is:

| State | Meaning |
| --- | --- |
| `ready` | The key, v15 policy, upload service, scanner, queue, worker, and storage are ready |
| `missing_access` | The tenant binding or required scopes are missing |
| `temporarily_unavailable` | Global submission or required infrastructure is not ready; retry later |
| `incompatible` | The client or deployed policy contract is incompatible and must be updated |

The response also returns `reason_code`, effective and missing scopes, ZIP limits, the pinned `protocolrev_dq_v15_15_0_0` policy, component readiness, and same-origin links. Create a submission only when `state` is `ready`.

## 2. Create one durable submission

Hash the ZIP with SHA-256, choose a stable idempotency key for this exact operation, and send:

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/api/v2/workspace-submissions" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: workspace-<stable-client-operation-id>" \
  --data '{
    "filename": "task-workspace.zip",
    "content_type": "application/zip",
    "size_bytes": 12345678,
    "sha256": "<64-lowercase-hex-characters>",
    "commit_policy": "automatic_when_eligible"
  }' \
  --output workspace-submission.json
```

A successful creation returns `201`, a `Location` header, `workspace_submission_id`, `state`, the existing upload-session projection under `upload`, and same-origin links for polling and upload controls. The current ZIP limit is `1 GiB`.

Reusing the same `Idempotency-Key` with the same body returns the same durable workflow. Reusing it with a different body returns `409 IDEMPOTENCY_KEY_REUSED`.

## 3. Upload the ZIP

Follow links from the response rather than constructing paths:

1. Call `links.sign_parts` to register archive part `1`.
2. Fetch the returned part capability. It contains a short-lived write-only resumable GCS session URI.
3. Upload the ZIP with resumable `PUT` requests and exact `Content-Range` headers. Do not send the Standard Data API key to GCS.
4. Call `links.finalize_parts` with part `1`, its exact size, and the final ETag.
5. Call `links.complete_upload` with an empty JSON object.

Audit binds the declared bytes and SHA-256, inventories ZIP entries, sanitizes paths and retained content, and scans the immutable object generation before mapping begins. Signed upload capabilities are bearer credentials: keep them in memory, never log or persist them, and discard them after upload.

## 4. Poll one workspace resource

Poll `links.self` with the Standard Data API key. Closing the browser does not stop server-side processing.

```bash
curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v2/workspace-submissions/workspacesubmission_..."
```

The durable states are:

```text
awaiting_upload -> uploading -> sanitizing -> mapping -> preflighting -> importing -> succeeded
```

`blocked`, `failed`, `expired`, and `cancelled` are terminal. The response progressively adds the sanitized source-bundle ID, adapter preview, public-safe v15 admission attestation, task import, blocking issues, and created task revision IDs.

The workflow imports all mapped tasks or none. Warnings do not block. Missing required checks, degraded evaluation, ambiguous mappings, review-required results, or any task blocker produce `blocked` and create no task revisions. Historical results in the ZIP remain supplied, unvalidated evidence unless a separate execution workflow validates them.

## Structured errors

Canonical v2 errors use this safe envelope:

```json
{
  "error": {
    "code": "MACHINE_STABLE_CODE",
    "message": "Safe summary",
    "request_id": "req_...",
    "retryable": false,
    "details": [{ "path": "/field", "code": "INVALID_FIELD" }],
    "links": {
      "regenerate_preview": "/api/v2/source-bundles/sourcebundle_.../adapter-previews"
    }
  }
}
```

`error.links` is optional and contains only bounded, same-origin API paths. When `code` is `PREFLIGHT_POLICY_CHANGED`, discard the stale preview and follow `links.regenerate_preview` with the documented adapter-preview request, or start a new workspace submission with the same corrected ZIP. Never display an API path as an end-user URL, and never follow an unknown relation or a cross-origin value.

| Status | Typical meaning |
| --- | --- |
| `401` | Missing, malformed, expired, inactive, or revoked credential |
| `403` | Missing tenant binding or required scope |
| `409` | Idempotency reuse, policy change requiring preview regeneration, or immutable mapping conflict |
| `422` | Invalid archive, blocked mapping, or failed v15 admission |
| `503` | Global submission mode or required infrastructure is unavailable; honor `Retry-After` |
| `421` | `/api/v2` was sent to a legacy task-feedback origin; retry against the returned canonical origin |

Do not convert every error to “not found.” Preserve the HTTP status, `error.code`, `request_id`, `retryable`, details, workflow stage, and `Retry-After` when presenting remediation.

## View imported revisions

After `state: "succeeded"`, use the tenant-scoped viewer endpoints:

```text
GET /api/v2/tasks
GET /api/v2/tasks/{task_revision_id}
GET /api/v2/tasks/{task_revision_id}/workspace
GET /api/v2/tasks/{task_revision_id}/files
```

An import creates new immutable revisions; it never edits an existing revision in place. Wilderness consumes these same records and presents the semantic Results, Solution, Environment, and All Files views.
