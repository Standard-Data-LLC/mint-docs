GDPx asks a practical question: can an agent finish realistic, economically useful work? Each task packages the job, source material, tools, expected work product, and a verifier that can explain the score.

## Know which package you are building

GDPx has two delivery layers. They serve different purposes and are not interchangeable.

| Layer | Purpose | Format authority |
| --- | --- | --- |
| Partner source handoff | Delivers runnable tasks, native rollout evidence, and review notes to Standard Data | The agreed partner layout and any adapter advertised for that delivery |
| Canonical GDPx submission | Creates immutable task and evidence records through the GDPx API | The live v3 capability response and linked JSON Schema |

<Warning>
  A partner handoff is not a canonical v3 review bundle. Standard Data may normalize an approved source layout, but no adapter can invent missing task files, trajectories, verifier evidence, work products, or identity bindings.
</Warning>

Before you build a ZIP for API submission, fetch the live contract:

```text
GET /api/v3/gdpx/capabilities
GET /api/v3/gdpx/schemas/review-bundle
```

If an example here differs from the deployed schema, follow the live response.

## The runnable task

Harbor is the default portable runtime format. A standard single-step task looks like this:

```text
<task-id>/
├── task.toml
├── instruction.md
├── environment/
│   └── Dockerfile
├── tests/
│   └── test.sh
└── solution/
    └── solve.sh                 # when a scripted reference is reasonable
```

Harbor's [task documentation](https://www.harborframework.com/docs/tasks) is the runtime schema authority.

### `task.toml`

Set the runtime, resources, timeouts, and verifier entry point. Pin every dependency that could change the task's behavior.

### `instruction.md`

Write the instruction the agent will see. Describe the outcome and constraints without exposing the solution or hidden grading material.

### `environment/`

Include the complete starting state and every source file the agent can see. The environment must build from the delivered files and reset cleanly between attempts.

### `tests/test.sh`

Run the verifier after the agent finishes. A direct GDPx Harbor delivery writes `/logs/verifier/reward.json` and keeps enough per-test evidence to explain the reward. An adapter advertised in the capability response may accept its documented native verifier output and normalize it into canonical evidence.

### `solution/solve.sh`

Provide a known-good path when a reference solution makes sense. A native reference artifact can replace the shell script when that better matches the work.

The agent must not be able to read the solution, hidden tests, or verifier-only material during the attempt.

## Scoring terms

| Term | Meaning |
| --- | --- |
| Verifier | The complete scoring system for the task |
| Deterministic checks | Code-based components of the verifier |
| Judge | An optional model-based verifier component for criteria that require practitioner judgment |
| Rubric | The observable criteria and aggregation rules used by the verifier |

## Evidence around the task

A runnable task is only the starting point. Every rollout used for QC or reported results must preserve:

- the exact task revision and agent-visible context;
- the ordered observable trajectory, including tool calls and results;
- the final answer and native work products;
- verifier and per-test output;
- criterion-level grading and score reconciliation;
- the model, harness, configuration, limits, timing, and outcome; and
- stable task, run, rollout, and artifact identities.

Do not collect or submit private chain of thought. Remove credentials, signed URLs, and provider-private fields, but keep the rest of the observable evidence intact.

See [Rollout viewer evidence](/gdpx/rollout-viewer-evidence) for the review surface.

## Choose the right path

### Send a source handoff

Use the [partner handoff layout](/gdpx/benchmark-task-package#partner-source-handoff) when Standard Data will normalize your delivery. Send it through the channel named in your onboarding agreement. Keep the complete native evidence in its original structure and include a file inventory or crosswalk. Before reorganizing an existing export, confirm the expected adapter with Standard Data.

Adapter acceptance means the source can be read. It does not mean the task passed QC or entered the benchmark.

### Submit a canonical v3 bundle

Use the [evaluation bundle contract](/gdpx/evaluation-bundle-upload) when you submit directly through the GDPx API. The canonical `TASK.json` is strict: rollout records live under `evaluations/`, not in a `rollouts` field inside `TASK.json`.

A `task_and_evidence` bundle carries one admission attempt for each included task. An `evidence_only` submission can attach the first QC1 attempt to an exact retained canonical Audit draft or retain a later attempt candidate for an already retained revision. That later candidate still needs separate operator admission and does not change the qualifying QC1 anchor. A QC3 campaign can contain many attempts, but they do not all belong in one canonical task record or one v3 bundle.

## The review sequence

GDPx uses four program review stages:

1. **QC1 — Construction integrity:** Standard Data runs or verifies one qualifying managed smoke attempt on the exact task revision.
2. **QC2 — Difficulty and reward integrity:** repeated attempts show a useful, non-saturated signal and a trustworthy verifier.
3. **QC3 — Benchmark evaluation:** the approved model–harness matrix is run on the frozen revision.
4. **QC4 — Release review:** Standard Data reviews results, normalizes accepted evidence, and decides final inclusion.

The v3 backend currently enforces QC1 requirements for the active evidence catalog. QC2 through QC4 remain separate program review gates. A record in the active evidence catalog does not enter the released GDPx benchmark until QC4 approves it.

See [QC stages](/qc-stages-for-benchmark) for definitions and [Partner delivery](/gdpx/benchmark-task-delivery) for responsibilities.
