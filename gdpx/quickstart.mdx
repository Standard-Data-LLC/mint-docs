GDPx measures whether an agent can complete realistic, economically useful work. A task includes the job, source material, tools, expected work product, and a verifier that can explain the score.

## Start with the two delivery layers

GDPx uses two related formats. They are not interchangeable.

| Layer | Purpose | Format authority |
| --- | --- | --- |
| Partner source handoff | Delivers runnable tasks, native rollout evidence, and review notes to Standard Data | The agreed partner layout and any adapter advertised for that delivery |
| Canonical GDPx submission | Creates immutable task and evidence records through the GDPx API | The live v3 capability response and linked JSON Schema |

<Warning>
  A partner handoff is not a canonical v3 review bundle. Standard Data may normalize an approved source layout, but an adapter cannot invent missing task files, trajectories, verifier evidence, work products, or identity bindings.
</Warning>

If you submit through the API, fetch the live contract before building the ZIP:

```text
GET /api/v3/gdpx/capabilities
GET /api/v3/gdpx/schemas/review-bundle
```

The live response wins if an example in these docs differs from the deployed schema.

## The runnable task

Harbor is the default portable runtime format. A standard single-step task looks like this:

```text
<task-id>/
├── task.toml
├── instruction.md
├── environment/
│   └── Dockerfile
├── tests/
│   └── test.sh
└── solution/
    └── solve.sh                 # when a scripted reference is reasonable
```

Harbor's [task documentation](https://www.harborframework.com/docs/tasks) is the runtime schema authority.

### `task.toml`

Define the runtime, resources, timeouts, and verifier entry point. Pin every dependency that can affect behavior.

### `instruction.md`

Write the instruction shown to the agent. Describe the outcome and constraints without exposing the solution or hidden grading material.

### `environment/`

Include the complete starting state and every agent-visible source file. The environment must build from delivered files and reset cleanly between attempts.

### `tests/test.sh`

Run the verifier after the agent finishes. A direct GDPx Harbor delivery writes `/logs/verifier/reward.json` and preserves enough per-test evidence to explain that reward. A capability-advertised adapter may accept its documented native verifier output and normalize it into canonical evidence.

### `solution/solve.sh`

Provide a known-good path when a reference solution is reasonable. A native reference artifact may replace a shell script when that better matches the work.

The agent must not be able to read the solution, hidden tests, or verifier-only material during the attempt.

## Scoring terms

- **Verifier:** the complete scoring system for the task.
- **Deterministic checks:** code-based components of the verifier.
- **Judge:** an optional model-based verifier component for criteria that require practitioner judgment.
- **Rubric:** the set of observable criteria and aggregation rules used by the verifier.

## Evidence around the task

A runnable task is necessary but not sufficient for a benchmark. Every rollout used for QC or reported results must preserve:

- the exact task revision and agent-visible context;
- the ordered observable trajectory, including tool calls and results;
- the final answer and native work products;
- verifier and per-test output;
- criterion-level grading and score reconciliation;
- the model, harness, configuration, limits, timing, and outcome; and
- stable task, run, rollout, and artifact identities.

Do not collect or submit private chain of thought. Remove credentials, signed URLs, and provider-private fields while retaining the rest of the observable evidence.

See [Rollout viewer evidence](/gdpx/rollout-viewer-evidence) for the review surface.

## Choose the right path

### Send a source handoff

Use the [partner handoff layout](/gdpx/benchmark-task-package#partner-source-handoff) when Standard Data will normalize the delivery. Send it through the delivery channel named in your onboarding agreement. Keep complete native evidence in its original structure and include a file inventory or crosswalk. Do not reorganize an existing export until Standard Data confirms the expected adapter.

Adapter acceptance means the source can be read. It does not mean the task passed QC or entered the benchmark.

### Submit a canonical v3 bundle

Use the [evaluation bundle contract](/gdpx/evaluation-bundle-upload) when you are submitting directly through the GDPx API. The canonical `TASK.json` is strict. Rollout records live under `evaluations/`; they do not belong in a `rollouts` field inside `TASK.json`.

A `task_and_evidence` bundle carries one admission attempt for each included task. An `evidence_only` submission can attach the first QC1 attempt to an exact retained canonical Audit draft or retain a later attempt candidate for an already retained revision. A later candidate requires separate operator admission and leaves the qualifying QC1 anchor unchanged. A QC3 campaign can contain many attempts, but those attempts do not all go into one canonical task record or one v3 bundle.

## The review sequence

GDPx uses four program review stages:

1. **QC1 — Construction integrity:** Standard Data runs or verifies one qualifying managed smoke attempt on the exact task revision.
2. **QC2 — Difficulty and reward integrity:** repeated attempts show a useful, non-saturated signal and a trustworthy verifier.
3. **QC3 — Benchmark evaluation:** the approved model–harness matrix is run on the frozen revision.
4. **QC4 — Release review:** Standard Data reviews results, normalizes accepted evidence, and decides final inclusion.

The v3 backend currently enforces the QC1 requirements for the active evidence catalog. QC2 through QC4 are separate program review gates. A record in the active evidence catalog is not part of the released GDPx benchmark until QC4 approves it.

See [QC stages](/qc-stages-for-benchmark) for definitions and [Partner delivery](/gdpx/benchmark-task-delivery) for responsibilities.
