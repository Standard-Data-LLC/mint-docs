Package each task in its own folder, with its runtime files and recorded evidence together. For a batch, group task folders by domain.

## Task layout

```text
<task-name>/
├── TASK.json                      # source metadata, when supplied
├── task.toml
├── instruction.md
├── environment/
├── tests/
├── solution/
├── steps/                         # multi-step tasks only
├── rollouts/<model-harness>/<run-id>/
│   ├── run.json
│   ├── traces/<trace-file>.json
│   └── artifacts/
└── qc/<run-id>/
    ├── run.json
    ├── traces/<trace-file>.json
    └── artifacts/
```

Add `rollouts/` and `qc/` records as runs become available. Include the actual evidence files, not pointers or omission notices.

| Path | What it contains |
| --- | --- |
| `TASK.json`, when supplied | Source task/revision identity, provenance, and associated run IDs |
| `task.toml` | Harbor runtime configuration and task metadata |
| `instruction.md` | The instruction shown to the agent |
| `environment/` | Build configuration, tools, and starting files |
| `tests/` | Verifier code and grading resources |
| `solution/` | Oracle/reference material |
| `rollouts/` | Model runs on this revision, grouped by model–harness pair |
| `qc/` | Oracle and no-op baseline runs, kept out of model success rates |

For a new task, provide its name, domain, source, and scoring intent in the task metadata. Preserve issued task and revision IDs when available; do not invent them or treat folder names as server IDs.

## The runnable task

Run Harbor against the individual task folder. Keep task-specific supporting files and any declared `steps/` tree intact. Use `task.toml` and any task-specific README for runtime requirements; [Harbor's task reference](https://www.harborframework.com/docs/tasks) explains the runtime fields.

A complete-looking folder does not prove readiness. Verify that dependencies are available, the reference check passes, and run evidence is complete. Use the [package checklist](/gdpx/benchmark-task-package) and [QC requirements](/qc-stages-for-benchmark).

## Read a result

1. Identify the exact task revision and run from the supplied metadata.
2. Open that run's `run.json` for configuration, status, and individual results.
3. Follow each result to its trace and native artifacts.
4. Separate scored model attempts from Oracle, baseline, and failed infrastructure attempts.

One run can contain several trials. Count individual valid subject attempts, not run folders.

## Task package versus API bundle

This task-and-evidence layout is for authoring and handoff. It is **not** the ZIP contract for `POST /api/v3/gdpx-submissions`.

Source metadata named `TASK.json` may contain `runs`. The API's canonical `TASK.json` is a different, strict task document; API run records live under `evaluations/`.

Use [Task packaging](/gdpx/benchmark-task-package) to prepare the task and [API bundle upload](/gdpx/evaluation-bundle-upload) when submitting directly. Build and validate the API bundle before uploading; do not send the task folder unchanged.
