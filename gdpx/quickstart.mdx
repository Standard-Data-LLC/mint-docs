Start with the [GDPx repository](https://github.com/Standard-Data-LLC/gdpx). It groups tasks by domain and keeps each task's runtime and recorded evidence together.

## Repository layout

```text
INDEX.json
<domain>/<task-name>/
├── TASK.json
├── task.toml
├── instruction.md
├── environment/
├── tests/
├── solution/
├── steps/                         # multi-step tasks only
├── rollouts/<model-harness>/<run-id>/
│   ├── run.json
│   ├── traces/<trace-file>.json
│   └── artifacts/
└── qc/<run-id>/
    ├── run.json
    ├── traces/<trace-file>.json
    └── artifacts/
```

Some exports have an `artifacts.SKIPPED.json` record instead of downloaded artifacts. Some large files use Git LFS. Neither is a substitute for the actual evidence bytes.

| Path | What it contains |
| --- | --- |
| `INDEX.json` | Task locations, rollout-run counts, QC-run counts, and solution presence |
| `TASK.json` | Exported organization, task/revision identity, source-package provenance, and run IDs |
| `task.toml` | Harbor runtime configuration and task metadata |
| `instruction.md` | The instruction shown to the agent |
| `environment/` | Build configuration, tools, and starting files |
| `tests/` | Verifier code and grading resources |
| `solution/` | Oracle/reference material |
| `rollouts/` | Model runs on this revision, grouped by model–harness pair |
| `qc/` | Oracle and no-op baseline runs, kept out of model success rates |

Domain folders include `biology`, `cybersecurity`, `finance`, `finance-onefinnet`, `hardware-engineering`, `healthcare`, `legal`, and `ml-and-infrastructure-engineering`. Read identity from metadata; a folder name is not a task or revision ID.

## The runnable task

Run the Harbor package inside the task folder, not the whole repository. Keep task-specific supporting files and any declared `steps/` tree intact. Use the package's `task.toml` and any task-specific README for runtime requirements; [Harbor's task reference](https://www.harborframework.com/docs/tasks) explains the runtime fields.

Repository presence does not prove readiness. A solution may be a placeholder, a dependency may need authorized retrieval, and a run may be incomplete. Check the [package](/gdpx/benchmark-task-package) and [QC evidence](/qc-stages-for-benchmark) before using a task.

## Read a result

1. Read `TASK.json` for the exact revision and run IDs.
2. Open that run's `run.json` for configuration, status, and individual results.
3. Follow each result to its trace and native artifacts.
4. Separate scored model attempts from Oracle, baseline, and failed infrastructure attempts.

One run can contain several trials. `INDEX.json` counts runs, not completed subject attempts.

## Repository format versus API format

The repository is a task-and-evidence export. It is **not** the ZIP contract for `POST /api/v3/gdpx-submissions`.

In particular, repository `TASK.json` is provenance metadata and may contain `runs`. The API's canonical `TASK.json` is a different, strict task document; API run records live under `evaluations/`.

Use [Task packaging](/gdpx/benchmark-task-package) for the repository structure and [API bundle upload](/gdpx/evaluation-bundle-upload) only when building a direct API submission. Do not zip the repository and assume the API accepts it unchanged.
