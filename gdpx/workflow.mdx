## 1. Start with the task folder

Prepare one folder per task using the [task layout](/gdpx/quickstart#task-layout). Include `task.toml`, the instruction, environment, tests, and reference material. Preserve any supplied task/revision metadata.

Keep the exact runnable package intact. Fix missing dependencies or placeholder reference material before claiming that it is ready to run.

## 2. Check construction

Build and reset the environment, run the reference/Oracle check, and run a no-op or known-bad control. Retain those results under `qc/<run-id>/`.

The `qc/` directory is baseline evidence, not a statement that all program QC stages passed. An Oracle failure needs diagnosis; it is not a model-capability failure.

## 3. Run and inspect model attempts

Keep model evidence under `rollouts/<model-harness>/<run-id>/`. Inspect each result, trace, verifier output, and native work product. Record failures and incomplete attempts honestly.

Changing task, environment, rubric, or verifier bytes creates a new revision. Do not attach old results to the new revision or infer difficulty from run-directory counts.

## 4. Use the right interface

| Goal | Interface |
| --- | --- |
| Prepare task files and evidence | [Task packaging](/gdpx/benchmark-task-package) |
| Get feedback on one task document | [`POST /v1/evaluate`](/gdpx/audit-endpoint) |
| Analyze one bounded, observable attempt | [`POST /v1/benchmark-rollout-analyses`](/gdpx/benchmark-rollout-analysis) |
| Submit a canonical Audit draft or evidence bundle | [`POST /api/v3/gdpx-submissions`](/gdpx/evaluation-bundle-upload) |

Neither feedback endpoint imports tasks or advances QC. Direct submission requires the API bundle format, with verified task identity and evidence bindings.

## 5. Deliver for review

Partners provide runnable source, rights and provenance, verifier logic, reference material, and any supplied run evidence. Standard Data reviews construction, difficulty, scoring, and release eligibility.

Use the delivery channel agreed for your task. For API submission, first check the live v3 capabilities and schema; then follow the returned upload, completion, and polling relations. Never send your API key to object storage.

See [Partner delivery](/gdpx/benchmark-task-delivery) for the checklist and [QC stages](/qc-stages-for-benchmark) for program decisions. A stored record or `review_ready` status is not final benchmark inclusion.
