Before a task enters QC, it must use the [benchmark task package](/gdpx/benchmark-task-package).

A draft or blocked task may remain in Audit. It cannot appear in GDPx/Wilderness until its exact current revision has one complete, approved QC1 rollout and an active immutable catalog membership.

## Partner task iteration

<Accordion title="QC1: Integrity in construction">
  Run one GPT-5.6 Luna smoke rollout through the approved managed execution path on the exact task and workspace inventory. Confirm that the environment, tools, source files, and verifier work. Retain the complete prompt, observable trajectory, final output, six forensic sections, criterion decisions, score reconciliation, native work products, and managed runtime receipt. The run counts only after Audit creates a matching operator-authenticated managed-execution approval. A trusted-runtime attestation rejection before model launch creates no subject rollout, no score, and no QC1 credit; retain only its bounded structural diagnostic. Fix construction or evidence-capture defects and repeat until one current-revision smoke is clean. Use [rollout analysis](/gdpx/benchmark-rollout-analysis) as judge-assisted evidence when the failure origin is unclear; it does not retain the rollout or advance the task.
</Accordion>

<Accordion title="QC2: Difficulty and reward integrity">
  Run repeated native frontier-harness rollouts. Confirm that rewards are stable, interpretable, and resistant to reward hacking. Review false positives and false negatives. If Luna is already saturated, keep the task in QC1, harden or drop it, and rerun. Saturated smoke results do not count as QC2.
</Accordion>

## Final benchmark evaluation

<Accordion title="QC3: Benchmark evaluation">
  Run 16 completed subject rollouts for each pairing in the current evaluation matrix. Analyze model failures, reward variance, unintended behavior, and verifier issues. Infrastructure retries, Oracle runs, and hinted runs do not count toward the 16 subjects.
</Accordion>

## Analysis and normalization

<Accordion title="QC4: Analysis and normalization">
  Review false positives and false negatives, cluster failure modes, run useful cross-harness checks, and decide final inclusion. Normalize accepted task and evidence revisions after that decision. Only a v3 submission with current rights authority, an approved managed QC1 execution, and current-policy `review_ready` status may join the active GDPx catalog.
</Accordion>

Internal-QA exact-byte evidence may support construction debugging and authenticated tenant review under its active grant. It cannot graduate into external GDPx membership. A catalog candidate needs the external publication authority and every normal QC admission requirement.

See [Partner delivery and review](/gdpx/benchmark-task-delivery) for the full evidence contract.

## Upload rollout evidence and analysis


Use this procedure for every benchmark rollout. A rollout is not delivered when
only its score, summary, or failure classification is visible. Delivery is
complete only when the exact attempt's primary evidence and its analysis are
retained together and can be read back from GDPx v3.

<Warning>
  Never upload a failure analysis without the rollout that it analyzes. Never
  use an analysis response as a substitute for logs, trajectory events, final
  output, verifier results, criterion decisions, or score reconciliation.
</Warning>

### Completion standard

For each attempted rollout, retain all of the following under one immutable
`task_revision_id`, `run_id`, and `rollout_id`:

- the exact task prompt, rubric, verifier identity, environment, and workspace inventory;
- the complete observable trajectory, including model messages, tool calls, tool results, environment events, errors, and stop condition;
- setup, controller, harness, agent, and verifier logs produced by the run;
- the final answer and every produced work product;
- raw verifier and test output;
- exactly one decision for every rubric criterion;
- score aggregation, threshold, hard gates, dependencies, and reconciliation;
- model, harness, environment, verifier, and judge versions;
- duration, turns or steps, tokens, cost, and execution outcome when the harness supplies them;
- exact artifact paths, byte sizes, media types, SHA-256 digests, and storage generations when available; and
- the rollout-analysis request, response, and a readable failure-analysis summary for every failed rollout.

"All logs" means all retained, reviewer-observable logs from the run. Omit
private model reasoning, credentials, bearer tokens, signed storage URLs, and
raw provider secrets. Redact only those prohibited values. Do not replace an
entire log with a summary because one line required redaction.

The six Wilderness forensic sections must all be present:

| Section | Minimum retained source |
| --- | --- |
| Problem | Exact task instruction and relevant agent-visible context |
| Setup Logs | Environment, dependency, materialization, and harness setup output |
| Agent Logs | Complete observable model and tool trajectory or a byte-bound complete trajectory artifact |
| Results | Final answer plus all declared work products |
| Test Logs | Raw verifier and test execution output |
| Grading | Criterion ledger, rationale, evidence references, and reconciled score |

Use `not_applicable` only when the source run genuinely produced no applicable
data, and include a source-grounded reason. Missing bytes that exist elsewhere
are not `not_applicable`.

### Keep evidence and analysis separate

These records serve different purposes and use different contracts:

| Record | What it proves | Where it belongs |
| --- | --- | --- |
| Canonical rollout evidence | What the agent, tools, environment, and verifier actually did | `RUN.json`, `ROLLOUT.json`, `trajectory.atif.json`, `verifier.json`, `criterion-decisions.json`, and `artifacts/` in a `gdpx-review-bundle/1.1.0` ZIP |
| Rollout-analysis request | The exact normalized evidence shown to the analysis judge | A hash-bound `supporting` artifact under the same rollout |
| Rollout-analysis response | The judge's classification, citations, legitimacy decision, recommendation, and fingerprints | A hash-bound `supporting` artifact under the same rollout |
| Failure-analysis summary | A reviewer-readable explanation derived from the retained evidence and analysis | A hash-bound `supporting` artifact under the same rollout |
| Managed execution receipt and approval | That Standard Data validated the exact execution and admitted its committed evidence | Operator-controlled records; an uploader cannot create these |

`POST /v1/benchmark-rollout-analyses` is synchronous and analysis-only. It does
not store the rollout, publish the response, create a v3 evidence record, or
make anything visible in Wilderness. You must retain its exact request and
response in the canonical evidence bundle.

<Info>
  The v3 source schemas are strict. Do not add analysis-only fields directly to
  `ROLLOUT.json`, `verifier.json`, or `criterion-decisions.json`. Retain the
  analysis as declared files in `artifacts/` and index those files in both
  `GDPX_BUNDLE.json` and `ROLLOUT.json`.
</Info>

### Compatibility of existing failure analysis

The failure analysis shown for **Bakers Dozen vs Ratings Landscape Reputation
Screen (Neutral)** is not the response produced by
`POST /v1/benchmark-rollout-analyses`.

The represented Bakers Dozen analysis uses the legacy
`finance-failure-analysis-v1` schema and the
`finance-failure-modes-reviewed-v1` taxonomy. It records a domain-specific
primary failure mode and criterion-category counts. The rollout-analysis
endpoint returns response schema `1.0.0`, including a closed DeepSWE tag,
failure legitimacy, first-failure locator, grounded citations, per-test root
causes, QC recommendation, judge identity, and input and output fingerprints.

The two records may analyze the same rollout, but they are not byte-compatible,
schema-compatible, or interchangeable. Do not mechanically translate one into
the other. Preserve the legacy record with its original schema and hash. If you
also call the endpoint, retain the new request and response as separate
artifacts bound to the same exact `task_revision_id`, `run_id`, and
`rollout_id`.

The endpoint output is compatible with the Wilderness backend only as retained
supporting evidence. It is not a canonical rollout, trajectory, verifier
report, criterion ledger, runtime receipt, or publication approval. Wilderness
can present it beside the canonical attempt after the bundle declares and
imports it; the endpoint call alone cannot make it appear.

#### What went wrong in the Bakers Dozen example

The Bakers Dozen record retained a classified failure-analysis object and score
metadata, while its Agent Logs, Setup Logs, and Test Logs were empty or
restricted. The original run still had observable trace, evaluation, and
controller-log bytes elsewhere. Analysis and primary evidence therefore became
separated.

For this kind of historical record:

1. recover the original bytes before considering a rerun;
2. bind them to the original task revision, run, and rollout;
3. build the missing trajectory, verifier, criterion, result, and forensic-section records without inventing data;
4. retain the legacy analysis unchanged as a supporting artifact;
5. optionally call the current analysis endpoint on a faithful observable projection and retain that response separately; and
6. submit and verify the repaired evidence through v3.

Run a new rollout only when the primary evidence cannot be recovered or the
task revision changed. Never attach a new run's evidence to the old rollout.

### Procedure

#### 1. Discover the deployed contract

Use the same API origin for capabilities, submission, readback, and catalog
verification:

```bash
export STANDARD_DATA_API_BASE="https://api.standarddata.io"
export STANDARD_DATA_API_KEY="<your-standard-data-api-key>"

curl --fail-with-body \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  "${STANDARD_DATA_API_BASE}/api/v3/gdpx/capabilities" \
  --output gdpx-capabilities.json
```

Do not build against a cached deployment assumption. Fetch the schema linked by
the live capability response and use only its advertised contract version,
accepted mode, adapter mode, size limits, and publication policy. The steps
below describe the current `gdpx-review-bundle/1.1.0` contract; stop if the
deployed capability response does not advertise it.

#### 2. Freeze the source attempt before analysis

Create a read-only inventory of every source file from the run. Record the
normalized path, byte size, media type, and SHA-256 for each file. Preserve the
original timestamps and execution identifiers separately when the harness
supplies them.

Before continuing, verify:

- one task revision maps to one exact task-content hash and workspace-inventory hash;
- every evidence record repeats the same task, run, and rollout identity;
- the trajectory is ordered and complete;
- the final answer and work products are the bytes that the verifier graded;
- the verifier result and every test output belong to that same attempt; and
- no retry, regrade, or reconstructed summary has overwritten the original bytes.

If the observable trajectory is too large for inline events, retain the full
trajectory as an artifact and point `trajectory.atif.json` to that exact
artifact. A truncated summary is not the complete agent log.

#### 3. Build the canonical evidence files

Use this layout for one publication-candidate attempt:

```text
GDPX_BUNDLE.json
tasks/<task_id>/TASK.json
tasks/<task_id>/PUBLICATION_AUTHORITY.json
tasks/<task_id>/task.toml
tasks/<task_id>/instruction.md
tasks/<task_id>/source/...
evaluations/<task_id>/<run_id>/RUN.json
evaluations/<task_id>/<run_id>/<rollout_id>/ROLLOUT.json
evaluations/<task_id>/<run_id>/<rollout_id>/trajectory.atif.json
evaluations/<task_id>/<run_id>/<rollout_id>/verifier.json
evaluations/<task_id>/<run_id>/<rollout_id>/criterion-decisions.json
evaluations/<task_id>/<run_id>/<rollout_id>/artifacts/...
```

`GDPX_BUNDLE.json` must inventory every other ZIP member. `ROLLOUT.json` must
declare every rollout artifact. The ZIP must contain exactly the bytes whose
sizes and hashes those records declare.

Follow the [evaluation bundle contract](/gdpx/evaluation-bundle-upload) for the
complete schemas and [rollout viewer evidence contract](/gdpx/rollout-viewer-evidence)
for the Master and six-section requirements.

#### 4. Analyze the exact failed rollout

For each failed rollout, create one strict analysis request from the frozen,
reviewer-observable evidence. Do not summarize away the first failure or any
failed verifier test. Do not include private reasoning or credentials.

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/v1/benchmark-rollout-analyses" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --data-binary @rollout-analysis-request.json \
  --max-time 200 \
  --output rollout-analysis-response.json
```

Validate that the response repeats the exact task revision, source run, and
rollout IDs. Retain the exact request and response even when the response says
`needs_human_review`. Resolve its `missing_inputs`; do not rewrite an ambiguous
result as a legitimate model failure.

See [Analyze a benchmark rollout](/gdpx/benchmark-rollout-analysis) for the
complete request, response, citation, and taxonomy contracts.

#### 5. Attach the analysis to the same rollout

Place the exact files under the rollout that they analyze:

```text
evaluations/<task_id>/<run_id>/<rollout_id>/artifacts/rollout-analysis-request.json
evaluations/<task_id>/<run_id>/<rollout_id>/artifacts/rollout-analysis-response.json
evaluations/<task_id>/<run_id>/<rollout_id>/artifacts/failure-analysis.md
```

Add each file to `GDPX_BUNDLE.json`. Also add an artifact descriptor to
`ROLLOUT.json` with the exact path, media type, byte size, and SHA-256. A safe
tenant-readable descriptor has this shape:

```json
{
  "artifact_id": "rollout-analysis-response",
  "path": "evaluations/example-task/run_example/rollout_example/artifacts/rollout-analysis-response.json",
  "name": "rollout-analysis-response.json",
  "media_type": "application/json",
  "size_bytes": 12345,
  "sha256": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "role": "supporting",
  "visibility": "tenant_reader",
  "sanitization": "sanitized",
  "contains_gold_reference": false
}
```

Use `tenant_reader` only when the exact file is sanitized and contains no gold
reference. If the analysis request or response contains an authorized
known-good answer, hidden test expectation, or other protected verifier
material, declare it `verifier_only` with the correct
`contains_gold_reference` value. Create a separate sanitized, source-grounded
summary for tenant readers when appropriate. Never mislabel protected bytes to
make them appear in Wilderness.

The readable `failure-analysis.md` should state:

- the exact task revision, run, and rollout IDs;
- the observed verifier outcome and score;
- the first observable failure with evidence references;
- every failed criterion or test and its evidence references;
- whether the cause belongs to the model, task, verifier, environment, provider, or orchestration;
- the endpoint's analysis ID, status, tag, legitimacy decision, confidence, recommendation, and input/output fingerprints; and
- any unresolved missing inputs or required rerun.

Do not paste a model-written explanation without citations. The exact JSON
response remains authoritative for what the endpoint returned.

#### 6. Validate and upload the bundle

Before creating a submission, validate every strict JSON schema, recompute all
hashes from the final bytes, check every evidence reference, and reconcile the
score from the criterion ledger. Then hash the exact ZIP and create one
idempotent submission:

```bash
curl --fail-with-body \
  --request POST "${STANDARD_DATA_API_BASE}/api/v3/gdpx-submissions" \
  --header "Authorization: Bearer ${STANDARD_DATA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: gdpx-<stable-client-operation-id>" \
  --data '{
    "filename": "delivery.zip",
    "content_type": "application/zip",
    "size_bytes": 123456,
    "sha256": "<64-lowercase-hex>",
    "contract_version": "gdpx-review-bundle/1.1.0",
    "mode": "task_and_evidence",
    "target_task_revision_id": null,
    "adapter_mode": "canonical",
    "publication_policy": "publish_when_review_ready"
  }' \
  --output gdpx-submission.json
```

Follow the same-origin upload, completion, polling, and cancellation relations
returned by the server. Do not construct storage URLs. Do not send the Standard
Data API key to object storage. Poll the returned `self` relation until the
submission reaches a terminal state, and retain the submission ID, exact source
ZIP hash, terminal state, and all issue codes.

Use `evidence_only` only when adding one immutable run and rollout to an already
retained, byte-identical task revision. It cannot replace task bytes or silently
change the current catalog.

#### 7. Prove readback before reporting completion

After import, retrieve the exact rollout:

```text
GET /api/v3/tasks/{task_revision_id}/runs/{run_id}/rollouts/{rollout_id}
```

Verify all of the following from the backend response and returned artifact
relations:

- task revision, run, and rollout IDs match the source attempt;
- score, threshold, outcome, test counts, and execution status match;
- Problem, Setup Logs, Agent Logs, Results, Test Logs, and Grading are all present;
- the complete trajectory, final answer, work products, verifier output, and criterion ledger are retrievable;
- every failed criterion has rationale and evidence references;
- the reported and calculated scores reconcile;
- every analysis artifact is listed under the same rollout;
- every downloaded artifact matches its declared byte size and SHA-256; and
- the analysis response's input and output fingerprints match the retained response.

Do not report success when an analysis is visible but any available primary
evidence is empty, restricted, missing, linked to another attempt, or represented
only by a summary.

#### 8. Distinguish retention from Wilderness publication

A successful upload or archive import does not make a rollout current in
Wilderness Results. Uploaded execution claims remain
`not_execution_validated` until the exact managed execution receipt and
operator approval exist. Publication additionally requires current review
readiness, immutable benchmark membership, and selection by the active catalog
head.

Verify these records when the rollout is intended to be current:

```text
GET /api/v3/tasks/{task_revision_id}/review-readiness
GET /api/v3/tasks/{task_revision_id}/runs/{run_id}/rollouts/{rollout_id}
GET /api/v3/gdpx/catalog/current
```

Wilderness reads the active v3 catalog. It must not infer current state from a
legacy fixture, release label, task head, run count, or upload flag. A task may
appear in **Review Tasks** as a retained draft while remaining absent from
**Results**.
