Every QC decision applies to one exact task revision. Changing the instruction, environment, source material, rubric, or verifier requires renewed review.

## Baseline runs are not stage labels

The repository's `qc/<run-id>/` contains Oracle and no-op baseline runs. Its name does not mean that QC1–QC4 passed.

Read `run.json`, its individual results, and referenced traces. A placeholder Oracle, failed baseline, or grader crash cannot establish solvability or difficulty.

Before program review, confirm that the environment builds and resets, a known-good check passes, and a no-op or equivalent negative control fails. Record any missing evidence.

## The four stages

| Stage | Review decision |
| --- | --- |
| QC1 — Construction integrity | The exact task runs reliably with its tools, reset behavior, verifier, and complete evidence capture |
| QC2 — Difficulty and reward integrity | Repeated valid attempts produce useful difficulty, with legitimate failures and a trustworthy verifier |
| QC3 — Benchmark evaluation | The approved model–harness matrix runs on the frozen revision |
| QC4 — Release review | Standard Data resolves material anomalies and decides inclusion, rework, or removal |

Standard Data runs or verifies the qualifying managed QC1 attempt. A partner-supplied run can support diagnosis but cannot approve itself. A passing smoke proves construction, not difficulty; one failure does not establish difficulty either.

If repeated valid attempts saturate the task, harden or remove it and review the new revision. Do not weaken the verifier to create or hide failures.

## Count attempts correctly

For QC3, follow the written campaign plan. The default is 16 completed subject attempts per task for each required model–harness pairing unless that plan specifies otherwise.

- Count individual valid model trials, not `INDEX.json` totals or run directories.
- Keep Oracle, no-op, hinted, and calibration attempts out of subject totals.
- Exclude setup failures, provider failures, voided trials, and duplicate retry records.
- Pin task, environment, verifier, model, harness, settings, and limits.

A repository run may contain several attempts. Its `qc/` and `rollouts/` folders are evidence storage, not an enforcement mechanism for the campaign's sample size.

## Evidence behind a decision

Retain the instruction, setup evidence, observable trajectory, final answer, native artifacts, verifier output, criterion decisions, and score reconciliation. Each failed attempt used in review needs a cited failure analysis.

Use [Rollout evidence](/gdpx/rollout-viewer-evidence) to check completeness. The optional [analysis endpoint](/gdpx/benchmark-rollout-analysis) provides supporting findings; it never advances a QC stage.

## API status is separate

Repository export status, Audit intake status, and program QC are different records.

| Signal | Meaning |
| --- | --- |
| Repository `TASK.json` or run folder | Exported identity and evidence; not certification |
| Audit draft retained | A draft is stored, possibly with blockers |
| API `review_ready` or active catalog membership | The API's technical admission requirements were met |
| Recorded QC4 decision | Standard Data approved release inclusion, rework, or removal |

The canonical Audit API does not itself certify the separate QC2–QC4 program decisions. Use the review tracker or written decision for those claims, and [API bundle upload](/gdpx/evaluation-bundle-upload) for intake details.
